A field guide for senior engineers

The Rendering Spectrum

Almost everything written about “SPA vs. MPA” gets the distinction wrong. It is not about page count. It is about how long your JavaScript runtime stays alive — and once you see that, the whole landscape from static HTML to local-first collaboration arranges itself on a single axis, and the architectural decisions stop being fashion.

This guide walks that axis end to end: the mechanism, the history that produced it, then the machinery you actually touch — history APIs, micro-frontend composition, bundlers, transports, auth, and delivery. Every non-obvious claim links to a primary source you can check.

Module 01 · Foundations

The dividing line

What actually separates a SPA from everything else — and why it has nothing to do with page count.

Ask ten engineers what makes an application a SPA and you get: one HTML file, client-side routing, no page reload. All symptoms. The cause is more specific.

Insight · The core distinction

The dividing line is what an interaction does to the JavaScript runtime.

Server-rendered: every interaction is a document replacement. Heap, DOM, variables, closures — all discarded, rebuilt from zero.

SPA: the document loads once and the runtime never dies. Navigation is a function call: swap components, push a URL, keep everything else.

Bundle size, SEO difficulty, hydration, API design, cache invalidation, the need for a client-side router at all — every one of those follows from that single property. Two definitions make it precise:

  • The runtime — the global object, the JS heap, the module registry, and every registration on the event loop.
  • What destroys it — a full document navigation, a hard reload, a crash, or the OS evicting a backgrounded mobile tab.

Runtime lifetime and state lifetime are different dials

The refinement most explanations skip. An MPA has a short runtime and a long state — the state lives in a server session, keyed by a cookie. The application is stateful; the browser is not. That decoupling is why MPAs worked for two decades and still do.

Separate the two dials and these architectures stop looking like a progression from primitive to modern. They become different answers to one question: where does the long-lived state live, and who is allowed to touch it?

Three rows that deserve more than a cell

htmx and Turbo are the sneaky case

The document persists, so the runtime persists — but the DOM underneath is destroyed and replaced on every fragment swap. Your setInterval and addEventListener outlive their targets. Hence Stimulus's connect()/disconnect() and htmx's htmx:load. Teams read "no client state" as "no lifecycle." It is not.

LiveView and Blazor Server are a third model entirely

Not a point between SPA and MPA: long-lived state held on the server, one process or circuit per open WebSocket, browser as thin diff-applier. Excellent on low-latency networks, punishing at 200 ms, and server memory now scales with concurrent users rather than request rate.

bfcache blurs the MPA boundary

Browsers freeze the entire heap on back-navigation and thaw it on return, so an MPA's runtime can survive a navigation. Module 05 has the mechanics and the two things that silently disqualify your page.

So — is a SPA only possible in a browser?

This is the right question, and the answer has two halves.

The half that is correct: “SPA” is defined negatively, against the browser's native navigation model. The term only carries meaning on a platform whose default behaviour is document replacement. Nobody describes an iOS app as a single-page application — not because it would be impossible, but because it is already how every native GUI app works.

The half that needs correcting: SPAs are not confined to a browser tab. They need a browser engine — Electron, Tauri, Capacitor, WKWebView, Android WebView. VS Code and Slack run on Electron; Spotify's desktop client uses CEF. All three are SPAs in an embedded browser wearing native window chrome.

Insight · The inversion

The SPA is not an innovation. It is the web re-converging on the normal GUI model — persistent runtime, in-memory state, event loop — that Smalltalk, Win32 and Cocoa had from the start.

The MPA is the anomaly: an architecture that destroys and rebuilds the entire UI after every click. It exists only because the web was a hypertext system drafted into being an app platform.

Recap
  • The distinction is runtime lifetime, not page count. Document replacement destroys the JS heap; SPA navigation does not.
  • Runtime lifetime and state lifetime are independent. MPAs have long-lived state — it lives on the server.
  • Long-lived state on the server, per connection, is a distinct third model, not a midpoint.
  • SPA requires a browser engine, not a browser tab. Conceptually it is the normal GUI model; the MPA is the anomaly.
Check yourself
  1. An htmx app has a long-lived runtime but is usually described as having “no client state.” Are those statements in conflict? What reconciles them?
  2. Your SPA works perfectly, then users report losing work after leaving the tab open overnight on mobile. Which property from this module explains it?
  3. Why is “LiveView is basically a SPA with the rendering on the server” a misleading description?
Answers
  1. No conflict — they describe different dials. The runtime is long-lived because the document is never replaced. The state is server-owned, and what client state exists lives in the DOM rather than in JS variables. The practical consequence people miss: a long-lived runtime means lifecycle is your problem. Listeners and intervals registered against swapped-out DOM keep running, which is why Stimulus has disconnect().
  2. Runtime lifetime is shorter than the session. “Whole session” is the optimistic case; mobile browsers discard backgrounded tabs under memory pressure and the JS heap goes with them. Anything that must survive needs explicit persistence and a rehydration path — the memory tier and the persisted tier are not the same thing.
  3. It puts LiveView on the SPA–MPA line, and it is not on that line. A SPA holds long-lived state in the browser. LiveView holds it in a server process, one per open socket, and ships DOM diffs. That changes what scales with what: your server memory now grows with concurrent users rather than request rate, and every interaction costs a round trip. Those are the properties that decide whether it fits, and the “SPA with server rendering” framing hides both.

Two things that are not on this axis

Progressive Web Apps are orthogonal. A service worker, a manifest, offline capability and installability can be bolted onto an MPA as easily as onto a SPA. PWA describes distribution and offline behaviour, not rendering.

Micro-frontends are also orthogonal, and more consequentially so. They are an organisational and deployment concern. You can build an MPA composed of independently-deployed SPAs — Module 06 argues that is usually the right shape. Confusing “we need micro-frontends” with “we need a SPA” produces some of the worst architectures in the field.

Insight · The one discriminator

How long is a session, and how dense are the interactions inside it?

Read-and-leave, low density → server-rendered HTML. Live-in-it-all-day, high density → SPA. Everything else is secondary, and both numbers are already in your analytics.

Recap
  • One axis: where the HTML is built and who holds the truth afterwards. Eleven recognisable positions on it.
  • PWA is orthogonal — it describes offline and installation, not rendering.
  • Micro-frontends are orthogonal and organisational. An MPA of independently-deployed SPAs is coherent and often correct.
  • Session length × interaction density settles most cases.
Module 03 · Foundations

How we got here

35 years in one timeline: the problems that caused each shift, not the frameworks that followed.

History matters here for a practical reason: nearly every architecture in Module 02 exists because a specific, identifiable pain made someone build it. Knowing which pain tells you whether you have that pain.

  • 1990 – 1993→ serverThe web is a document system

    Hypertext, links, no application model whatsoever. Every navigation is a fresh request for a file. This is the ground state the rest of the story reacts against.

  • 1993→ serverCGI

    HTML becomes generated per request; forms give you input. The application server is born, and with it the first stateless-protocol problem.

  • 1995 – 2000→ serverJavaScript ships; the classic MPA crystallises

    PHP, ASP and JSP explode. Session cookies solve statelessness. POST/Redirect/GET becomes the pattern for form handling. Anything genuinely “rich” goes to Java applets or Flash, because the DOM cannot do it.

  • 1999→ clientXMLHTTP ships in Internet Explorer 5

    Built by Microsoft's Outlook Web Access team. It sits largely unnoticed for five years — the capability existed well before anyone built a culture around it.

  • 2004 – 2006→ clientGmail, Google Maps, and the naming of AJAX

    Two products prove partial page updates work at scale. Jesse James Garrett names the technique in February 2005. jQuery arrives in 2006 and makes the DOM and XHR bearable for ordinary teams.

  • 2010→ clientBackbone.js — “SPA” enters the vocabulary

    The first widely-adopted client-side MVC — and the reason URLs looked like example.com/#!/users/42 for several years.

    Why the #: changing any part of the URL before the hash triggers a page load. The fragment is the one part that does not — by design it is a pointer into the current document, so it is never sent to the server and changing it fires hashchange instead of a request. Before pushState, it was the only writable part of the URL.

    Why that broke: since the server never sees the fragment, /#!/users/42 and / are the same request. Every route in the application was one URL as far as a crawler was concerned, so none of them could be indexed.

    The patch: Google's 2009 proposal gave #! a special meaning — on seeing it, the crawler would re-request the page as ?_escaped_fragment_=/users/42, a normal URL the server does see, and the server was expected to answer with a pre-rendered HTML snapshot. You therefore had to run a headless renderer server-side just to be indexed.

    Both the hack and the patch died with pushState. Google deprecated the scheme in October 2015, by which point Googlebot could render JavaScript itself.

  • 2012→ clientThe History API lands broadly

    The actual enabling technology. pushState() gives you real URLs without a reload. Before this, SPAs were a hack with a fragment identifier; after it, a legitimate architecture. Everything in Module 05 starts here.

  • 2013 – 2016→ clientReact, and the SPA as unexamined default

    AngularJS then React: virtual DOM, unidirectional data flow. Webpack, Babel and npm make the build pipeline both powerful and enormous. The SPA stops being a choice and becomes the starting template.

  • 2016 – 2020→ serverThe bill arrives

    Bundle size, time-to-interactive, SEO, broken back buttons, accessibility regressions on low-end mobile hardware. The answer is to push work back to the server: SSR with hydration (Next.js, 2016), static generation, and the PWA push for offline.

  • 2020 – 2024→ serverThe correction

    htmx and Hotwire revive hypermedia. Astro popularises islands. Svelte and Solid attack the runtime cost directly. React ships Server Components. Simultaneously the browser closes the gap natively: bfcache, speculation rules, cross-document View Transitions.

  • 2026→ clientConvergence, and the Navigation API

    “SPA vs MPA” is no longer an application-wide decision — serious meta-frameworks let you set it per route. And the Navigation API reached Baseline in January 2026, finally giving the platform one central place to intercept navigation. Fourteen years after pushState, the API SPAs actually needed has arrived.

Insight · Read the oscillation

Server, server, server — then a long swing to client through the 2010s — then back from 2016.

Each swing answers a constraint the previous swing created, and those constraints are still there. The counter-arguments from the previous swing were not refuted. They were outvoted.

Recap
  • The capability for AJAX existed in 1999 and the culture arrived in 2005. Capability and adoption run on different clocks.
  • pushState (2012), not any framework, is what made SPAs architecturally legitimate.
  • The 2016+ swing back toward the server was driven by measurable costs, not taste.
  • The field is converging on per-route decisions rather than per-application ones.
Module 04 · Foundations

Choosing an architecture

Six drivers, how to measure the first one, and what each side honestly costs.

The drivers, in priority order

  1. Session length and interaction density. Established in Module 02 as the discriminator. Measure it rather than guessing.
  2. Content or application. Public, indexable, first-visit-matters content pulls toward server rendering. Authenticated tools pull toward the client.
  3. Offline and latency requirements. A hard offline requirement settles the question immediately.
  4. Team shape. One full-stack team with a server language is a strong signal for hypermedia. A separate frontend team plus multiple clients consuming one API amortises the SPA's cost.
  5. Client device constraints. Low-end mobile and emerging markets punish JavaScript far harder than your development laptop suggests.
  6. Existing API needs. If a public or mobile API already exists, the SPA's biggest structural cost is already paid.

How to actually measure driver 1

Saying “measure session length and interaction density” is useless without the recipe. Both numbers are usually already in your analytics, or are two lines of instrumentation away.

These thresholds are judgement, not research. They are calibrated to be roughly right at the extremes, which is where the decision is actually easy; the middle band is where drivers 2 through 6 do the work.

What a SPA actually costs

Trap · You are reimplementing the browser

Routing, history, scroll restoration, focus management, loading indicators, caching, error pages, form resubmission semantics, link prefetching. The browser gave you every one of these for free, correctly, and accessibly. You now own them all, and you will get several of them subtly wrong.

  • A second source of truth. Server database plus client cache, and keeping them consistent is now your problem. This is the entire reason TanStack Query, SWR and Apollo's cache exist — most "SPA complexity" is cache-invalidation complexity under another name.
  • A larger XSS blast radius. One injection lands in a long-lived session with credentials in memory. Module 10 covers why this compounds in micro-frontends.
  • Version skew. Users run last week's bundle against today's API. You need a build-identifier header and a "new version available" path — before you need them.
  • Accessibility work MPAs get free. Route changes are not announced to screen readers unless you announce them. Focus does not move unless you move it.
  • Memory leaks become real. Detached DOM nodes, orphaned subscriptions, retained closures. You will need to profile.

What an MPA or hypermedia approach costs

  • Latency per interaction. On a high-RTT connection this is the whole experience.
  • A ceiling on interaction richness. Drag-and-drop canvases, real-time collaborative editing and offline work are not reasonable to build this way.
  • Client state discarded on navigation. Scroll position, half-filled forms, media playback. bfcache and View Transitions have narrowed this considerably (Module 05), but not closed it.
  • More server work per interaction, and harder to put behind a CDN.
Insight · The real disagreement

When a team is torn between these, the argument is rarely technical. It is where the team wants its complexity to live: in a build pipeline and a client cache, or in server round-trips and a rendering layer.

Both are legitimate. Neither makes complexity disappear.

Recap
  • Six drivers, led by session length × interaction density. The rest are tiebreakers.
  • The SPA's dominant hidden cost is reimplementing browser behaviour, followed by owning a second source of truth.
  • The MPA's dominant cost is per-interaction latency and a ceiling on interaction richness.
  • The choice is about where complexity lives, not whether you will have any.
Check yourself
  1. A team proposes a SPA for a public product catalogue with high organic search traffic and a median session of ninety seconds. Which two drivers argue against it, and what would you propose instead?
  2. Why does “we already have a mobile app” materially change the calculus?
  3. Name the three browser behaviours you would have to reimplement first, and which is most often done badly.
Answers
  1. Session length and content-vs-application — drivers 1 and 2. A ninety-second median session means the user pays the bundle cost and leaves before amortising it, and high organic search traffic makes first paint and indexability the product. Propose static generation or server rendering with islands for the interactive parts — filters, gallery, add-to-cart. That is the Netflix result in Module 02: the landing page got 50% faster by removing client-side React, not by tuning it.
  2. Because the SPA's largest structural cost is already sunk. A mobile app forces you to have an API, versioned and public, plus the server-side cache and auth story that goes with it. Driver 6 is really asking whether you are paying for that twice. If you already have it, the marginal cost of a web SPA is much lower — and conversely, building a SPA in order to have an API is paying for a second client you do not have.
  3. Routing, history and scroll restoration first — they are entangled and everything else depends on them. Then focus management, loading state, and error pages. The one most often done badly is focus management on route change: the browser moves focus to the new document automatically, a client router does not, so keyboard and screen-reader users are left focused on a link that no longer exists. It is invisible in QA unless someone tests without a mouse.
Module 05 · The machinery

Location, history, URL

History, its traps, the Navigation API that replaces it, and what breaks when several routers share one address bar.

The History API and its three documented traps

history.pushState(state, unused, url) is the call that legitimised the SPA. MDN documents three behaviours that routinely surprise people.

It fires nothing

From the source

pushState() never causes a hashchange event to be fired.

— MDN, History.pushState(). It does not fire popstate either — only user-initiated traversal does. This is exactly why every micro-frontend framework has historically monkey-patched history.

The state object has a size cap

From the source

Some browsers save state objects to the user's disk so they can be restored after the user restarts the browser, and impose a size limit on the serialized representation of a state object, and will throw an exception if you pass a state object whose serialized representation is larger than that size limit.

— MDN. MDN does not print the number; the widely-cited Firefox figure traces to Bugzilla. See Appendix C.

It is rate-limited

MDN lists a SecurityError Thrown if… the method is called too frequently. The specific thresholds are not specified anywhere normative — MDN has an open issue to document them. This matters the moment you sync a scroll position, a slider or a map viewport into the URL.

Also worth knowing: history.scrollRestoration, with values "auto" and "manual", is the switch you flip when your router and the browser are fighting over scroll position.

The Navigation API — the genuinely new thing

This is the most significant change to web navigation since pushState, and it crossed the availability line recently: MDN marks it Baseline 2026, “Newly available” since January 2026.

From the source

This is a successor to previous web platform features such as the History API and window.location… specifically aimed at the needs of single-page applications (SPAs).

And on the central capability: the navigate event is fired when any type of navigation is initiated, meaning that you can control all page navigations from one central place, ideal for routing functionality in SPA frameworks. (This is not the case with the History API…)

— MDN, Navigation API

Beyond that central interception point it adds intercept() for handling a navigation with custom behaviour including scroll and focus control, entries() for the real same-origin history list, and traverseTo(key). Documented limitations: no navigate event on first load, single-frame only, and you cannot delete or rearrange entries.

Insight · Why this matters for micro-frontends

Every micro-frontend framework patches history.pushState for one reason: the History API never fired an event for programmatic navigation. No hook existed, so frameworks manufactured one.

The Navigation API removes that need. Build new shells on the navigate event, not on a decade of monkey-patching.

The surrounding navigation platform

bfcache

From the source

The most important way to optimize for bfcache in all browsers is to never use the unload event. Ever!

And, critically for this guide's thesis: Because bfcache works with browser-managed navigations, it doesn't work for 'soft navigations' within a single-page app (SPA).

— web.dev, Back/forward cache. Cache-Control: no-store on the document also disqualifies it.

Read that second quote next to Module 01: a well-built MPA gets instant back-navigation from the platform, for free. Your SPA has to build it.

Speculation Rules

The Speculation Rules API declares prefetch and prerender intent as JSON, either in a <script type="speculationrules"> block or via the Speculation-Rules header. This is what lets a well-tuned MPA feel instant. Chromium-led; support elsewhere is unconfirmed here (Appendix C).

Cross-document View Transitions

Both documents opt in with @view-transition { navigation: auto; } and the browser animates between them — smooth transitions with no client-side router. But MDN currently marks @view-transition as “Limited availability… because it does not work in some of the most widely-used browsers.” Firefox has not shipped it.

Ground has moved — carefully

“MPAs can now feel like SPAs” is a popular 2025–2026 claim and it is partly true. bfcache and speculation rules are broadly available. Cross-document View Transitions are not — they work in Chromium and Safari and not in Firefox. Design the navigation to be correct without the transition and treat the animation as an enhancement.

What the browser did for free, and your router does not

Module 04 lists “reimplementing the browser” as the SPA's largest hidden cost. This is the concrete version, and it is the part most often shipped broken — because it is invisible unless you test without a mouse.

On a real navigation the browser does four things automatically. A client-side router does none of them:

Insight · The Navigation API knows about this

This is the second reason to build new routing on the Navigation API rather than pushState. Its intercept() takes options for focus and scroll handling, with sensible defaults, so the platform does the resetting instead of each router reinventing it.

Under pushState this behaviour did not exist to inherit — which is a large part of why a decade of SPAs shipped without it.

Several routers, one address bar

This is the concrete mechanism behind “how do micro-frontends share the URL,” and where a lot of production pain lives.

From the source

single-spa fires PopStateEvent events when it wants to instruct all active applications to re-render. This occurs when one application calls history.pushState, history.replaceState, or triggerAppChange.

— single-spa API documentation

So the mechanism is: patch history, tag the synthetic events (evt.singleSpa = true), and rebroadcast a single popstate so every child router re-evaluates. Applications declare URL ownership through an activity function — a pure function… called with window.location as the first argument returning whether that app should be active. A urlRerouteOnly option, default true, stops pushState calls that do not change the route from triggering a reroute.

Trap · What breaks without a single owner

From micro-frontends.tech: When each micro frontend has its own router (e.g., React Router), conflicts arise: Duplicate history entries — Each router may push its own state. Scroll restoration — Multiple routers can fight over scroll position. Route change events — The shell needs to know when a micro frontend navigates internally.

Real instances: Vue Router #3152 (multiple instances cannot independently clean up popstate listeners) and Angular #47789.

The recommended resolution from that same source: The shell owns the primary History API interaction. Micro frontends receive the current path as a prop and render accordingly, or use hash-based sub-routing to avoid conflicting with the shell.

Recap
  • pushState fires no event, has an unspecified size cap, and is rate-limited. All three are documented and all three surprise people.
  • The Navigation API reached Baseline in January 2026 and gives you one central interception point — build new shells on it.
  • bfcache gives MPAs instant back-navigation free and explicitly does not apply to SPA soft navigations. unload handlers and Cache-Control: no-store disqualify you.
  • Cross-document View Transitions are not yet in Firefox. Treat as enhancement.
  • One router owns history; everyone else receives the path. This is the rule.

Micro-frontends

When to split a frontend, where to compose it, and everything that gets harder once you do.

Insight · Start here or waste a year

Micro-frontends solve exactly one problem: N teams need to deploy independently onto one URL surface. They are Conway's law (Melvin Conway, 1967) expressed as a build system.

Three teams and one deploy pipeline? You do not have this problem. Do not pay the cost.

From the source

If your teams can deploy together and you mainly want faster builds, runtime composition is the wrong tool for that problem.

Trap · “Selective SSR” means three different things

It is not a standard term, and people use it for at least three unrelated mechanisms. Establish which one is meant before agreeing to anything:

  1. Per-route rendering choice — some routes server-rendered, others static or client-only. The most common meaning, entirely standard, and every meta-framework has it: Next.js route segment config, Nuxt routeRules, SvelteKit's export const ssr = false. Nothing exotic.
  2. Partial prerendering — selective within one page: a static shell plus dynamic holes, in one response. This is what PPR above is.
  3. Selective hydration — React's term, and not an SSR mode at all. It is about which parts get JavaScript and in what order (Module 07). Routinely conflated with the other two because the word is the same.

All three are current and widely used. They solve different problems, and a conversation where one person means (1) and the other means (3) will appear to agree and then produce the wrong architecture.

Which modes survive composition

This is the part that is absent from most micro-frontend writing, and it is where the real constraint lives:

Insight · The cacheability floor

A composed page is only as cacheable as its least cacheable fragment.

One team's per-user fragment makes the whole assembled document uncacheable at the CDN — unless the composition layer caches each fragment separately. That single property decides which composition pattern you can afford.

Composition patternWhat happens to the SSR modes
Routing-level zones All five survive, independently. Each zone is a whole application with its own cache policy — team A can be fully static, team B can run PPR, and neither constrains the other. This is the strongest argument for zones that nobody makes.
Server fragment composition Survives, but you must do the work. Every fragment needs its own TTL and the layout must honour it — this is precisely what ESI was invented for, and what Podium's manifest and context headers carry. Streaming is the natural fit. The trap: fragments then have different ages on one page, which is fine for nav and footer and dangerous for price next to stock level.
Federated SSR Mostly collapses. One render, one response, one cache policy. ISR and PPR both assume a single build knows which parts are dynamic, and a remote that decides at runtime breaks that assumption. In practice you fall back to request-time SSR for the whole page, losing the CDN entirely.
Trap · Crawlers take a different code path

Under PPR, bots do not get the cached shell. From the same docs: because they need a complete document, Next.js skips the shell and renders the entire page dynamically at request time.

So your SEO traffic exercises a different rendering path from your users, and work that completed during prerendering now runs at request time for a bot. A page that loads fine for a person can fail for a crawler if the shell depended on build-time data. In a composed page, that failure mode is multiplied by the number of teams contributing to the shell.

SSR with micro-frontends: three patterns

1. Fragment services — when SEO and first paint matter

Each micro-frontend exposes an HTTP endpoint returning an HTML fragment plus its asset manifest. A layout service fetches them in parallel and streams them into one document as they arrive. Module 07 covers the mechanics.

2. Routing-level split — the pragmatic default

Each micro-frontend owns a URL prefix and is a complete, independent application behind a reverse proxy. Next.js formalises this as Multi-Zones; plain Nginx does it too.

From the source

Multi-Zones are an approach to micro-frontends that separate a large application on a domain into smaller Next.js applications that each serve a set of paths. … Since applications are decoupled, Multi-Zones also allows other applications on the domain to use their own choice of framework.

And the behaviour you must design around: Navigating between pages in the same zone will perform soft navigations… Navigating from a page in one zone to a page in another zone… will perform a hard navigation. Consequently, Links to paths in a different zone should use an a tag instead of the Next.js <Link> component.

— Next.js, Multi-Zones

This is an MPA of SPAs, and it is dramatically more robust than the alternatives: no shared bundler configuration, no runtime version negotiation, independent failure domains. The cost is one full page load when crossing a zone boundary — and with speculation rules and View Transitions that boundary is now nearly invisible.

3. Federated SSR — most seamless, most operationally expensive

The host imports remote modules over the network at request time and renders everything into one tree. Your server render now has a network fan-out on the critical path, so you need remote-entry caching, version pinning, and a degraded mode for every remote. It works. It is not where you start.

Worth its own treatment, because Next.js is where most teams ask this question and because the options divide cleanly into build-time (one deployable, no independent release) and runtime (separately deployed, assembled when a request arrives). The versioning trap

A shared design-system package looks like the obvious answer and quietly reintroduces the coupling the architecture was meant to remove. Insight · Split tokens from components

Ship design tokens at runtime; ship components at build time.

Tokens — colour, spacing, type scale, radius — go out as CSS custom properties served by the shell. Change a brand colour centrally and every micro-frontend picks it up on next load, with nobody redeploying.

Components stay a versioned package each team upgrades on its own schedule. A team lagging two versions looks slightly dated; it does not look like a different product, because the tokens underneath are current.

And the detail that makes this work with Shadow DOM: custom properties inherit through shadow boundaries where stylesheets do not. Tokens are the one thing that can cross the isolation you just paid for.

Two operational rules worth adopting early. Prefix everything — class names, custom element names, CSS custom properties, localStorage keys — with the owning team's name; this is one of the core practices on micro-frontends.org and costs nothing to start with and a great deal to retrofit. And one team owns global CSS: resets, @font-face, :root tokens, and nothing else is allowed at document scope.

Sharing state: a ranked ladder

Insight · The governing principle

The best shared state is no shared state. (Not original here — a common formulation in the field.)

If two micro-frontends share a lot of mutable state, they are not two micro-frontends. You drew the boundary along screen regions instead of business domains. Redraw it before picking a mechanism.

  1. The URL. Wildly underrated and almost always sufficient. Selected entity, filters, active tab, pagination, sort order. Zero coupling, no library, survives reload, deep-linkable, and the browser maintains it for you. Exhaust this before anything else.
  2. Server state, not client state. Most “shared state” is cached server data in disguise. Two micro-frontends that both need the cart count should both ask the API, backed by a shared HTTP cache (ETag, Cache-Control) or one shared query-client instance. Reframing shared state as shared cache is the single biggest lever available to you.
  3. Events. CustomEvent on window; BroadcastChannel for cross-tab and cross-iframe. Version the contracts (cart:item-added@v1).
  4. One small shell-owned singleton. Not a global Redux store — a deliberately tiny, versioned contract for what is genuinely cross-cutting: auth/session, theme, locale, feature flags, notifications. That list is close to complete.
  5. Props down, events up, if your micro-frontends are custom elements. It is just the DOM contract, and it is the cleanest boundary available.
  6. Web storage for tokens and preferences only. A poor reactive store: no same-tab event, strings only, quota limits.
Trap · Events are not state

A micro-frontend that mounts after an event fired never sees it, and will render with stale or empty data. This produces bugs that only appear under specific navigation orders and are miserable to reproduce.

Always pair a broadcast with a “read the current value” accessor. The event says something changed; the accessor answers what is it now.

Anti-patterns worth naming: a shared global Redux store (you rebuilt the monolith, then distributed its deploys); importing another micro-frontend's internals; and passing React context across a federated boundary where React is not a singleton — see Module 08.

Recap
  • Micro-frontends solve independent deployment for many teams. Nothing else. If that is not your problem, stop.
  • Composition point is the real taxonomy: build-time, server, edge, or runtime.
  • Seamlessness and decoupling trade against each other directly. Choose deliberately.
  • Routing-level split is the pragmatic default; fragment streaming when SEO demands it; federated SSR last.
  • The state ladder starts at the URL and at treating shared state as shared cache.
Module 07 · The machinery

Fragment streaming and hydration

How streaming works on the wire, why fragments hydrate themselves, and what Server Components change.

The mechanism, from the primary source

The authoritative explanation is Dan Abramov's “New Suspense SSR Architecture in React 18” in the official React working group. Two passages carry the mechanism.

From the source

When the data for the comments is ready on the server, React will send additional HTML into the same stream, as well as a minimal inline <script> tag to put that HTML in the 'right place'.

And the property that makes it composition-friendly: Unlike traditional HTML streaming, it doesn't have to happen in the top-down order… when the sidebar HTML is ready, React will stream it along with the <script> tag that inserts it in the right place — even though the HTML for the post (which is further in the tree) has already been sent! There is no requirement that data loads in any particular order.

— React 18 Working Group, Discussion #37

So the wire format is: shell HTML containing placeholders, then hidden HTML blocks appended near the end of the document, then a tiny inline script that relocates each block into its slot. React explicitly credits prior art — Marko is one of JavaScript web frameworks that implements a version of this pattern — linking to eBay's engineering writeup, a second independent description of the same technique.

The APIs: renderToPipeableStream for Node streams and renderToReadableStream for Web streams. React's term for the synchronous part: The part of your app outside of any <Suspense> boundaries is called the shell.

What actually goes over the wire

The part that is hard to picture from prose. A single HTTP response, arriving in pieces, where a later piece repairs an earlier one.

t0 · server Render begins. Everything outside a <Suspense> boundary — the shell — is synchronous and ready immediately.
t0 · flushed Shell HTML goes out: header, nav, layout, and a placeholder where each pending boundary sits. The browser starts painting now, before any data has resolved.
t0 · flushed The bundle downloads in parallel. Hydration of the shell can begin before the rest of the document has arrived.
t1 · server The sidebar's data resolves — even though the post below it in the tree is still pending. Order of completion, not order of markup.
t1 · flushed Two things append to the same still-open response: a hidden <div> holding the sidebar's real HTML, and a minimal inline <script>.
t1 · browser That script runs the instant it is parsed and moves the hidden block into the placeholder's slot. The sidebar pops in. React need not have loaded yet — this step works without it.
t2 · server The post resolves. Same two-part append, same relocation. Response closes.
t2+ · browser Selective hydration attaches behaviour per boundary, prioritising whatever the user has already clicked.

Two consequences worth holding onto. Content arrives in the order the data resolves, so one slow fragment delays only itself. And the relocation is plain DOM work by an inline script, so the HTML is complete for a crawler even with the framework absent.

Per-fragment hydration — supported, with a caveat

From the source

An app fully built with React will usually only have one hydrateRoot call with its root component.

But the API explicitly provides for the other case. On the identifierPrefix option: A string prefix React uses for IDs generated by useId. Useful to avoid conflicts when using multiple roots on the same page.

— react.dev, hydrateRoot
Trap · One root means one blast radius

If the whole page hydrates from a single root, one team's hydration error blanks the entire page — including the fragments that rendered perfectly. In a page owned by several teams, that is an unacceptable coupling of failure domains.

Use one hydration root per fragment, and give each a distinct identifierPrefix or you will get duplicate DOM ids from useId.

Why hydration mismatches happen

The characteristic failure of every architecture in this module: the server rendered one tree, the client rendered a different one, and React discards the server's work and re-renders. Slower than not server-rendering at all, and often silent in development.

The causes are a short and finite list:

  • Values that differ between the two renders — Date.now(), Math.random(), crypto.randomUUID(). Anything non-deterministic in render.
  • Locale and timezone. The server formats a date in UTC, the browser in the user's zone. The single most common cause in production, and invisible to a developer sitting in UTC.
  • Reading window, localStorage or matchMedia during render instead of in an effect. The server has no equivalent, so branches diverge — a theme toggle reading stored preference is the classic.
  • Invalid HTML nesting. A <div> inside a <p>, or a <p> inside a <p>. The parser silently corrects the server's HTML, so the real DOM no longer matches what React expects. Baffling until you know it.
  • Browser extensions mutating the DOM before hydration. Not your bug, but it produces the same error report.
  • Duplicate ids across fragments — the composition-specific one. Two independently hydrated subtrees using useId without distinct identifierPrefix values, exactly as above.

Two of these bite composed pages harder than single applications. Locale is usually resolved by the shell and must be propagated to every fragment — Podium's context headers again — or team A renders in the user's locale and team B in the server's default. And a mismatch inside one fragment only destroys that fragment, provided you took the one-root-per-fragment advice above; with a single root it takes down the page.

Islands are the same idea at a different granularity

Astro's documentation describes islands as rendering the majority of your page to fast, static HTML with smaller 'islands' of JavaScript added when interactivity or personalization is needed on the page. The lineage is documented there too: the term came from Etsy's Katie Sylor-Miller in 2019, expanded in Jason Miller's August 2020 post.

From the source

This may seem similar to 'micro-frontends' at first glance. Both approaches share the idea of breaking applications up into independent units, however 'micro-frontends' do not typically imply that composition of those units is achieved using HTML.

And the isolation property that makes per-fragment hydration robust: Each part of the page is an isolated unit, and a performance issue in one unit doesn't affect the others.

— Jason Miller, “Islands Architecture”

Podium is the maintained equivalent, and its vocabulary is worth learning: In Podium there are two types of servers: Podlets that serve page fragments / Layouts that compose podlets and serve the finished page. Server Components, and why they belong in this guide

Module 02 lists them as a row on the spectrum, which undersells them. They change the shape of the axis itself, and they do it by attacking the property Module 01 is built on.

A third runtime category

Module 01 gave two answers to “how long does the runtime live”: one document, or the whole session. A server component is neither. It runs once on the server, renders to a serialized payload rather than JavaScript, and never exists on the client at all. No bundle entry, no hydration, no memory footprint. Its lifetime is a single render.

So 'use client' is not a rendering hint. It is the literal marker for where the client runtime begins — the network boundary expressed as a component boundary. Everything above it costs zero client JavaScript; everything below it is a SPA.

The property that is genuinely new

Navigation under RSC does not replace the document and does not re-render the client tree from scratch. The router fetches a new payload for the changed part and merges it into the existing client tree.

Server renders each navigationClient state survives navigation
Classic MPAYesNo — heap destroyed
SPANo — client rendersYes

That bottom row is the point. Server rendering on every navigation, without losing in-memory client state — an open modal, a media player, a half-filled form all survive. No previous position on the spectrum offers both, and it is why RSC is not simply “SSR with extra steps.”

What it costs

  • The spectrum stops being a per-application choice. It becomes a per-component dial, which is more power and considerably more ways to be inconsistent across a codebase.
  • The boundary is invisible in the source. A 'use client' three components up silently pulls everything below it into the bundle. Bundle regressions arrive as a one-line diff in an unrelated file.
  • Data fetching moves into rendering, which removes an API layer and removes the place many teams had put their caching and authorization.

And why it does not yet compose across teams

RSC and micro-frontends are not currently compatible in the way people assume. An RSC payload is a serialized React tree tied to a specific React version and a specific build — a tighter coupling than sharing a JavaScript module, not a looser one. Module Federation's maintainers describe RSC support as validated in demos and not shippable (Module 08).

The pattern that does work today is the one in Module 06: a server component fetching another team's rendered output over HTTP. That crosses the boundary as data or HTML rather than as a React tree, which is exactly why it survives the version skew.

Recap
  • Server components are a third runtime category: rendered once per request, shipped as a payload, never present on the client.
  • 'use client' marks where the client runtime starts — the network boundary as a component boundary.
  • They are the only position that server-renders every navigation and preserves client state.
  • They do not federate. The payload is more tightly version-coupled than a JS module, not less.
  • Out-of-order streaming works by appending hidden HTML plus a tiny inline script that relocates it. React documents this; Marko did it first.
  • Hydrate per fragment, not per page, and set identifierPrefix — one root couples every team's failure domain.
  • Islands are the same technique at component granularity; Jason Miller's post distinguishes them from micro-frontends precisely.
  • Tailor is archived. Podium, OpenComponents, Piral and qiankun are alive.
  • Per-fragment timeouts, fallbacks and error boundaries are not optional — one slow team must not block the page.

Sharing semantics, the React singleton problem, working setup code, and which tools are dead ends.

The shared configuration, precisely

Trap · A widely-repeated wrong default

A large number of blog posts state that strictVersion defaults to false. The official documentation says it defaults to true when a local fallback exists and the module is not a singleton. Trust the doc; this determines whether your build fails loudly or degrades silently.

The React singleton problem, stated correctly

“You must share React as a singleton” is the standard advice and it is slightly wrong in a way that matters.

From the source

In order for Hooks to work, the react import from your application code needs to resolve to the same module as the react import from inside the react-dom package. If these react imports resolve to two different exports objects, you will see this warning.

And the nuance most summaries drop: In general, React supports using multiple independent copies on one page (for example, if an app and a third-party widget both use it). It only breaks if require('react') resolves differently between the component and the react-dom copy it was rendered with.

— react.dev, Invalid hook call warning

So two fully independent micro-frontends, each with their own React, are fine — provided nothing crosses the boundary. It is sharing components, context or hooks across the boundary that forces the singleton, and therefore forces the version coupling micro-frontends were supposed to eliminate. That is the tension from Module 06 in its most concrete form.

Trap · The subpath that silently duplicates React

From Module Federation's documentation: Writing 'react-dom' (no trailing slash) only intercepts import 'react-dom'. Any code that does import { createRoot } from 'react-dom/client' will load a second copy of React DOM, which breaks React singleton requirements and causes hydration errors.

Every modern React 18+ codebase imports from react-dom/client. This will bite you.

Two applications: a remote (cart) that exposes a component, and a host (shell) that loads it at runtime. Nothing is linked at build time — the host has no cart in node_modules.

Both sides now need an async boundary at the entry point. Shared modules resolve asynchronously, so a synchronous entry cannot use them — this two-file dance is the single most common setup error.

What happens when that page loads:

  1. Shell boots and populates its share scope with the versions of react and react-dom it carries.
  2. On first render of <CartWidget />, the runtime fetches remoteEntry.js from cart.example.com.
  3. The remote registers its versions into the same share scope and negotiates: because both declare singleton, one copy of React wins — the higher semver, with a console warning to the loser.
  4. The runtime fetches only the chunks for ./CartWidget that are not already satisfied.
  5. The component renders inside the shell's React tree, sharing its context and its reconciler.
Trap · Step 2 is a network call you do not control

If cart.example.com is slow or down, that dynamic import() rejects and — without the error boundary above — takes down the shell's whole subtree. Every remote needs a boundary and a fallback. The team that owns the shell will be paged for the team that owns the remote.

The three main alternatives, in code

All three solve the same problem — load another team's code at runtime — and differ in who does the resolving.

1. Import maps — the browser resolves

Module 09 · The wire

APIs and transports

What the browser can actually speak, and the two transport problems that only appear with several teams.

The two micro-frontend-specific problems

Trap · The connection budget

From MDN on EventSource: When not used over HTTP/2, SSE suffers from a limitation to the maximum number of open connections, which can be specially painful when opening various tabs as the limit is per browser and set to a very low number (6). The issue has been marked as 'Won't fix' in Chrome and Firefox.

Six micro-frontends each opening their own EventSource on HTTP/1.1 and the user has zero connections left for anything else — in every tab.

Rule: the shell owns one connection and fans messages out. Micro-frontends do not each open their own.

Trap · You cannot authenticate a WebSocket with a header

The browser constructor is new WebSocket(url) / new WebSocket(url, protocols). There is no headers parameter. You cannot send Authorization.

That leaves cookies (which flow automatically), a subprotocol hack, or a token in the query string — which lands in access logs. And cookies flowing automatically is itself the problem: per OWASP, Browsers include cookies in WebSocket handshake requests, making WebSocket applications vulnerable to Cross-Site WebSocket Hijacking (CSWSH).

The mitigation is explicit: Validate the Origin header on every handshake. Always use an explicit allowlist of trusted origins. See also CWE-1385.

Why gRPC cannot work in a browser

From the source

It is currently impossible to implement the HTTP/2 gRPC spec in the browser, as there is simply no browser API with enough fine-grained control over the requests. For example: there is no way to force the use of HTTP/2, and even if there was, raw HTTP/2 frames are inaccessible in browsers.

— grpc.io, “The state of gRPC in the browser”

gRPC signals its final status in HTTP/2 trailers, which fetch cannot read. gRPC-Web works around it with a mandatory translating proxy, usually Envoy. Connect is the cleaner modern answer: Bidirectional streaming requires HTTP/2, but the other RPC types also support HTTP/1.1. The protocol doesn't use HTTP trailers at all, so it works with any networking infrastructure.

From the source

Passing SDP objects to remote peers is called signaling and is not covered by the WebRTC specification… You can use anything you like, from WebSocket to fetch() to carrier pigeons.

So WebRTC is never your only transport — you always need a second one to bootstrap it. RTCDataChannel is the non-media use: peer-to-peer arbitrary data.

GraphQL federation and subscriptions

Apollo Federation's vocabulary: the single, federated graph is called a supergraph; the constituent APIs are called subgraphs; Clients make requests to the federated GraphQL API's single entry point called the router. The property that makes it fit micro-frontend org structures: Different subgraphs in the same supergraph can use different server implementations and even different programming languages.

On subscriptions, the over-HTTP spec explicitly punts: GraphQL Subscriptions are beyond the scope of this specification at this time. The live transports are graphql-ws and graphql-sse.

Ground has moved

  • Browser WebSockets cannot carry an Authorization header, and the cookies they do carry create CSWSH. Validate Origin against an allowlist.
  • gRPC is impossible in a browser because raw HTTP/2 frames and trailers are inaccessible. Use Connect, or gRPC-Web with a proxy.
  • WebRTC always needs a second transport for signalling.
  • SSE for server-push-only; WebSocket for genuine bidirectional; WebTransport is newly Baseline.
Module 10 · The wire

Auth and session

Tokens, cookies, CSRF, sessions and logout — the one-way door, against the IETF's August 2026 BCP.

RFC 10017, “OAuth 2.0 for Browser-Based Applications” was published on 21 August 2026 as a Best Current Practice. It sits in BCP 212 alongside RFC 8252 (native apps) — worth stating because BCP numbers can contain several RFCs and this is easy to get wrong.

Three architectures, ranked by the RFC itself

From the source · Pattern 1, BFF

A browser-based application that relies on a backend component for handling OAuth responsibilities and forwards all requests through the backend component ('Backend for Frontend' or 'BFF').

Its three responsibilities: act as a confidential OAuth client; manage OAuth access and refresh tokens in the context of a cookie-based session, avoiding the direct exposure of any tokens to the browser-based application; and forward all requests to resource servers, augmenting them with the correct access token.

Verdict: This architecture is strongly recommended for business applications, sensitive applications, and applications that handle personal data.

— RFC 10017 §6.1

Pattern 2, token-mediating backend: the backend does OAuth but the browser calls resource servers directly with the token. From a security perspective, the token-mediating backend is less secure than a BFF but still offers significant advantages over an OAuth client application running directly in the browser.

Pattern 3, browser-based OAuth client: everything in the browser. If an attacker is able to execute malicious code in the browser, this application architecture is vulnerable to all attack scenarios discussed earlier… This architecture is not recommended for business applications, sensitive applications, and applications that handle personal data.

The cookie checklist

§6.1.3.2 is unusually prescriptive for an RFC. Treat it as a literal checklist:

  • The BFF MUST enable the Secure flag for its cookies.
  • The BFF MUST enable the HttpOnly flag for its cookies.
  • The BFF SHOULD enable the SameSite=Strict flag for its cookies.
  • The BFF SHOULD set its cookie path to /.
  • The BFF SHOULD NOT set the Domain attribute for cookies.
  • The BFF SHOULD start the name of its cookie with a prefix indicating the cookie was set via HTTP, for example, by using the __Host-Http- prefix.
Ground has moved · The Domain rule

The common advice for micro-frontends is “set a cookie on the shared parent domain so every sub-app can use it.” The RFC says not to, and it is right.

A cookie without Domain is host-only: If omitted, the cookie is returned only to the host that sent it. With Domain=example.com it is readable by every subdomain, so one compromised subdomain compromises the session everywhere. __Host- prefixed cookies structurally cannot carry Domain at all.

The reconciliation: the BFF design makes the parent-domain cookie unnecessary rather than merely forbidden. If all API traffic is proxied through the BFF's own origin, a host-only cookie already reaches everything. Needing a Domain cookie is a signal that you have sub-apps calling different backends directly — that is the smell, not the cookie.

Trap · SameSite=Strict and inbound links

A Strict cookie is not sent on cross-site navigation. A user following a link from email or a partner site arrives logged out until a same-site request fires. The RFC still says Strict — so handle it with a silent re-authentication bounce, not by quietly downgrading to Lax.

CSRF — the bill that comes with cookie sessions

This guide has recommended cookie-based sessions throughout, and until now said nothing about the class of attack that recommendation reopens. A cookie is attached by the browser automatically, on requests your application did not initiate. That is the entire point of a cookie and the entire mechanism of CSRF.

Bearer tokens in JavaScript were immune to this, because an attacker's page cannot read your memory to construct the header. Moving to cookies trades an XSS exposure for a CSRF exposure. You have to close the second one deliberately.

Trap · SameSite=Strict is not a CSRF defence on its own

The most common mistake after adopting a BFF: assuming the cookie flags from the checklist above finished the job. OWASP is direct about this:

SameSite is useful as a defense-in-depth control but it does not replace a proper CSRF defense in most deployments.

The gap that matters most for micro-frontends is the second one they list: SameSite is scoped to the registrable domain, not the origin. A cookie set on app.example.com with any SameSite value is still considered “same-site” when the request originates from anything.example.com.

If your teams deploy to sibling subdomains — which is exactly what a micro-frontend estate looks like — every sibling is inside your same-site boundary. OWASP names the amplified version: an attacker who claims a dangling subdomain can issue requests that your SameSite-protected cookies will accompany.

Their other documented gaps, each worth checking against your own estate:

  • Lax only blocks unsafe methods. If any state-changing operation in the application is reachable via a GET request, SameSite=Lax will not stop it. This is the single most common way SameSite-based defenses fail in practice.
  • Top-level navigation tricks. window.open, a crafted link or a prerender hint can produce a request the browser treats as same-site.
  • Coverage is not universal. Older and embedded browsers may behave as if no SameSite value were set.
  • Client-side CSRF is untouched. SameSite reasons about cross-site requests; it does nothing about your own same-origin JavaScript being manipulated into a state-changing call.

What to actually implement

OWASP's summary recommendation, in order:

  1. Use your framework's built-in CSRF protection if it has one. If not, add CSRF tokens to all state-changing requests... and validate them on the backend.
  2. Stateful backend → synchronizer token. Generated server-side, per session or per request. Per-request is stronger, at some usability cost.
  3. Stateless backend → signed double-submit cookie, and specifically the signed variant: Simply signing tokens without session binding provides minimal protection and remains vulnerable to cookie injection attacks. Always bind the CSRF token explicitly to session-specific data. The naive double-submit pattern is documented by OWASP as discouraged for new code.
  4. Send the token in a custom request header, not a form field. Since requests with custom headers are automatically subject to the same-origin policy, it is more secure to insert the CSRF token in a custom HTTP request header via JavaScript. For an API-shaped BFF this is the natural fit, and a custom header alone is a legitimate defence for AJAX endpoints.
  5. Verify Origin, falling back to Referer, on every state-changing endpoint. These are forbidden headers that only the browser can set. OWASP recommends blocking when neither is present.
Insight · Where this lives in a micro-frontend

The BFF already owns the session, so it must also own CSRF. One token, minted by the BFF, exposed to micro-frontends through the shell's getCsrfToken() — the same tiny shell-owned contract from Module 06, extended by one method.

Per-micro-frontend CSRF tokens are the failure mode here. They multiply the surface, they break the moment one team's token is rotated by another team's request, and they tempt somebody into widening the cookie's Domain to share them — which reintroduces the exact subdomain weakness above.

Sessions, not just tokens

The chapter so far has been about OAuth architecture. The session itself has its own lifecycle, and OWASP's session management guidance covers the parts that are easy to skip.

Rotate the session ID on privilege change

A new session identifier must be issued at login, and again at any privilege elevation — step-up MFA, entering an admin context, impersonation. This is the defence against session fixation, where an attacker plants a known session ID before the victim authenticates and inherits the authenticated session afterwards. Reusing the pre-login identifier is the vulnerability.

OWASP also warns against the condition a micro-frontend estate creates by default: it is recommended not to mix web applications of different security levels on the same domain. Vulnerabilities in one of the web applications would allow an attacker to set the session ID for a different web application on the same domain by using a permissive Domain attribute. A third argument against the Domain cookie, from a different direction.

Logout has to invalidate the server side

From the source

When a session expires, the web application must take active actions to invalidate the session on both sides, client and server. The latter is the most relevant and mandatory from a security perspective.

— OWASP Session Management Cheat Sheet

Clearing the cookie is the cosmetic half. A logout that only deletes the client cookie leaves a session that still validates if the value was captured. In a BFF, one logout must clear the cookie, destroy the server-side session record, and revoke the refresh token at the authorisation server — otherwise the BFF can mint a new access token for a user who believes they have left.

And logout has to propagate

Two propagation problems that only appear once the frontend is split:

  • Across micro-frontends in one tab. The shell logs out; every mounted micro-frontend still holds rendered user data and possibly an open socket. The shell needs to broadcast a session:ended event and each micro-frontend must clear and unmount on it — the same event contract from Module 06, and the one case where ignoring the event is a security bug rather than a staleness bug.
  • Across tabs. Other tabs keep rendering a logged-in UI against a dead session until their next request fails. BroadcastChannel or the storage event closes it. This is also the mechanism for the reverse case: a login in one tab should refresh the others rather than leaving them in a stale anonymous state.

Where authorization lives

Everything above is authentication. Authorization is a separate decision that micro-frontend teams routinely leave implicit, and there are only three places to put it.

Auth during server rendering

Expanding the one-line rule from earlier, because this is where composed pages leak.

  • Propagate, do not re-authenticate. The inbound request's identity travels to every internal call and every fragment render — Podium's context headers (Module 07) exist for exactly this.
  • Never cache user data at module scope. In a long-lived Node process, a module-level variable is shared across every concurrent request. This is the highest-severity bug in this entire guide: it serves one user's data to another, it passes every test that runs one request at a time, and it appears under load.
  • An authenticated render is not CDN-cacheable, which is the cacheability floor from Module 06 arriving as a security constraint rather than a performance one. Keep the personalised part behind its own boundary and stream it.
  • Decide what a mid-stream auth failure renders. Once the shell has flushed, you cannot send a redirect — the status line is long gone. The fragment must degrade to a signed-out state inside its own boundary, and the shell must be designed to survive that.

Token storage — the RFC is blunt

From the source

On localStorage: localStorage does not protect against unauthorized access from malicious JavaScript, as the attacker would be running code within the same origin, and as such, would be able to read the contents of the localStorage.

On JavaScript-readable cookies: this practice is NOT RECOMMENDED.

And the honest general conclusion: none of these options can fully mitigate token exfiltration when the attacker can execute malicious code in the application's execution environment.

Also non-negotiable: Browser-based clients MUST use the Authorization Code grant type and MUST NOT use the Implicit grant type to obtain access tokens.

— RFC 10017 §8
Insight · Why this compounds in micro-frontends

N teams' code, one origin, one JavaScript heap. Every micro-frontend sits inside every other one's XSS blast radius. A third-party dependency added by any team can read what any other team put in memory.

The strongest argument for keeping tokens out of the browser entirely — stronger here than in a monolith.

Supporting specs and the practical rules

  • RFC 9700 (BCP 240, not 212): Refresh tokens for public clients MUST be sender-constrained or use refresh token rotation. Also The resource owner password credentials grant [RFC6749] MUST NOT be used.
  • Foundations: RFC 6749 (framework), RFC 6750 (bearer tokens), RFC 7636 (PKCE).
  • The shell owns token refresh. Never let each micro-frontend run its own refresh loop — you get a thundering herd on expiry and a race on rotation that logs users out at random. Common, and very hard to diagnose.
  • Proxy API calls through one origin rather than configuring CORS with credentials across N origins. Note a wildcard origin is rejected when credentials are used — the server must echo the specific origin.
  • Deduplicate the fan-out. Five micro-frontends each calling /me on load is the signature performance bug of this architecture.
  • On the server side: SSR calls go over the internal network, propagate the inbound auth context and a trace ID, and never cache user data at module scope — in a long-lived Node process that is a cross-user data leak.

Third-party cookies: the ground moved twice

Ground has moved

If your micro-frontends live on different origins or in iframes, this matters directly. Chrome reversed the third-party cookie deprecation, and in an October 2025 Privacy Sandbox post announced it is retiring most of the replacement APIs — including Topics, Protected Audience, Attribution Reporting, Related Website Sets and Shared Storage.

What survives: CHIPS and FedCM… We'll continue to support those APIs. We'll also maintain Private State Tokens. So CHIPS / partitioned cookies is the durable mechanism for cross-origin embedded micro-frontends.

Recap
  • RFC 10017 (Aug 2026) strongly recommends the BFF for anything sensitive, and does not recommend a pure browser OAuth client for it.
  • Cookies: Secure + HttpOnly MUST; SameSite=Strict, path /, __Host-Http- prefix and no Domain SHOULD.
  • Cookies reopen CSRF. SameSite is defence in depth, not a defence — it is scoped to the registrable domain, so every sibling subdomain is inside your boundary. Add a signed double-submit or synchronizer token, in a custom header, plus Origin verification.
  • Rotate the session ID at login and at every privilege change. Run both an idle and an absolute timeout — idle alone never expires an active attacker.
  • Logout must destroy the server-side session and revoke the refresh token, then propagate across micro-frontends and across tabs. Clearing the cookie is the cosmetic half.
  • Authorization is enforced at the resource server. The browser gets coarse capability flags for rendering, never the role graph, and never enforcement.
  • During SSR: propagate identity, never cache user data at module scope, and decide in advance what a mid-stream auth failure renders.
  • No token storage in the browser is safe against XSS — and micro-frontends enlarge the blast radius.
  • The shell owns refresh. One origin for API traffic. Deduplicate /me.
  • Third-party cookies survive in Chrome; CHIPS and FedCM are the surviving Privacy Sandbox pieces.
Module 11 · The wire

Monorepo and delivery

Does a shared repo defeat independent deployment? No — and here is what you need to run it.

Insight · Two things people conflate

Repo layout and deploy independence are orthogonal.

One repository couples your source history, not your deployments. Only the first is affected by directory layout. Confusing the two drives most of this argument.

The two positions

Cam Jackson's article assumes separate repositories per micro-frontend, each with its own pipeline. Nx argues the opposite, and makes the stronger case:

From the source

A monorepo removes two of the biggest micro frontend pains: shared dependency drift and cross-app integration testing. Every application builds against the same library versions at the same commit, and CI exercises the composed application before any team deploys. Deployments stay independent even though the repository is shared.

And on the dominant failure mode: Because deployments are not atomic, mismatched shared library versions are a leading failure mode of micro frontends. The safest strategy is to share only the libraries that must be singletons.

— Nx, Micro Frontend Architecture

Vercel states the principle neutrally, and most cleanly: Microfrontends work the same whether you keep your applications in one repository (a monorepo) or spread them across several (a polyrepo)… Each application is its own Vercel project and deploys on its own, no matter where its code lives.

Turborepo

Ground has moved · Domain

Current Turborepo documentation lives at turborepo.dev. Both turbo.build and turborepo.com redirect there. Vercel's own docs are one migration behind and still show the pre-2.0 "pipeline" key instead of "tasks" — do not copy their turbo.json snippets.

  • Remote Caching — a cloud server that stores the results of your tasks… preventing duplicated work across your entire organization. Without it, the same task must be re-executed on each machine.
  • turbo prune — Generate a partial monorepo for a target package, emitting only the needed source, a pruned lockfile and the root package.json. With --docker it splits output for layer caching. This is how you get a small container image per micro-frontend out of a large repository.
  • Filtering — ...ui selects dependents of ui, ui... selects ui and its dependencies. --affected is shorthand for --filter=...[main...HEAD] and requires a deep checkout, or all packages will be considered changed.
Trap · The microfrontends proxy is dev-only

Turborepo's microfrontends support is narrower than the name suggests: The Turborepo microfrontends proxy is meant for local usage only. How you implement and integrate your production microfrontends depends on your production infrastructure.

The same page draws the distinction crisply: The proxy composes independently running applications by route. Module Federation composes JavaScript modules at runtime inside an application.

Nx — and a breaking change you need to know about

Ground has moved · The big Nx break

As of Nx v23, the host and remote generators are replaced by consumer and provider. Deprecated in v23 and removed in v24: @nx/react:host|remote|federate-module, @nx/angular:host|remote|setup-mf, and all module-federation-dev-server and module-federation-ssr-dev-server executors. There is no automated codemod.

Angular: Angular Module Federation in Nx is no longer supported. Use @angular-architects/native-federation for the supported Angular path going forward. SSR: SSR is not first-classed in the new generators… If you need SSR with federation, see the upstream Module Federation SSR guide and wire it yourself.

Any tutorial using nx g @nx/react:host or Nx SSR module federation is citing a dead API. This is the single most consequential piece of staleness in the current ecosystem.

For scale evidence, Nx publishes named customer stories — Caseware at 700+ projects and Broadcom at 177. Treat the compute-savings figures in them as vendor-reported rather than audited. Turborepo has no equivalent published case study I could verify; the company names circulating for it come from an unmoderated community thread, so this guide does not repeat them.

Nx's other machinery remains excellent: nx affected, computation caching that restores both the terminal output and the files, and enforce-module-boundaries — how you stop teams importing each other's internals. That last one is the governance layer micro-frontends need and rarely have.

Package managers and release

  • pnpm workspaces — the workspace: protocol: When this protocol is used, pnpm will refuse to resolve to anything other than a local workspace package. Note Yarn's publish semantics differ: workspace:* publishes as an exact pin.
  • Phantom dependencies — pnpm's rationale: When installing dependencies with npm or Yarn Classic, all packages are hoisted to the root of the modules directory. As a result, source code has access to dependencies that are not added as dependencies to the project. In a micro-frontend repository this is genuinely dangerous: an app builds locally against a hoisted transitive dependency and fails only in isolated production builds.
  • Changesets — an intent to release a set of packages at particular semver bump types. For applications rather than npm packages, see their versioning-apps guide.
  • Bazel rules_js — warranted at very large scale or in polyglot repositories. Note rules_js is an alternative to build_bazel_rules_nodejs… which is now unmaintained.

Knowing what is actually running

Rarely planned and always needed. Once deployments are independent, nobody knows what combination of versions a given user saw — and that single fact makes production debugging qualitatively harder than in a monolith, where the answer was one commit SHA.

Four things to put in from the start, all cheap before launch and painful after:

  • Publish every build ID. Each micro-frontend writes its name and build identifier somewhere machine-readable — a <meta> tag, a global registry object, a response header. The first question on any incident is “which versions were live together,” and without this it is unanswerable.
  • Propagate one trace ID. The shell mints it and every fragment render and every API call carries it. Otherwise a slow page is six unrelated traces and no way to see that fragment C blocked the render.
  • Attribute errors to an owner. Tag every reported error with the owning micro-frontend and its build ID, and upload source maps per team. Untagged errors land on whoever owns the shell, who cannot fix them — the most reliable way to burn out a platform team.
  • Attribute performance too. One team's bundle regression shows up as the whole page's LCP getting worse. Without per-micro-frontend attribution in your RUM, the shell gets blamed for a change it did not make.
Trap · The version-combination explosion

Five micro-frontends on independent release cadences produce a combinatorial space of live version sets, and your integration tests exercise exactly one point in it: the newest of everything.

Two mitigations. Test the composed application in CI at the current production versions, not at HEAD of everything — that is the combination your users have. And keep a deliberately short compatibility window, an explicit rule such as “any micro-frontend must work against shell contracts from the last 30 days,” so the space stays bounded rather than growing forever.

Deployment

Vercel's monorepo docs describe the mechanism most platforms converge on: one project per application directory, and Vercel automatically skips builds for projects in a monorepo that are unchanged by the commit. The requirement that makes it work is worth quoting because it is what teams get wrong: Dependencies between packages in the monorepo must be explicitly stated in each package's package.json — otherwise every commit deploys everything.

Recap
  • Repository layout and deployment independence are orthogonal. A monorepo buys atomic cross-library refactors and pre-deploy integration testing at no cost to deploy independence.
  • Turborepo's microfrontends proxy is local-development only. Docs are at turborepo.dev.
  • Nx v23 replaced its entire micro-frontend generator surface and dropped Angular MF and SSR-MF. Most tutorials online are now wrong.
  • pnpm prevents phantom dependencies, which matter more here than in a single app.
  • Per-app affected builds require explicitly declared inter-package dependencies.

The decision sequence

  1. Measure session length and interaction density. This settles the SPA question more often than any architectural debate will.
  2. Ask whether independent deployment is a hard requirement. If teams can ship together, do not build micro-frontends. You want faster builds, and runtime composition is the wrong tool for that.
  3. If it is a hard requirement, choose your composition point before choosing any tool.
  4. Design auth before anything else. It is the hardest thing to retrofit and the most damaging to get wrong. RFC 10017 gives you a checklist — §6 for the architecture, §6.1.3.2 for the cookie flags.
  5. Pick tooling last. By this point the constraints have narrowed the options to one or two.

Module 13 · In practice

Migration paths

Nobody is greenfield. Four routes people actually take, ordered so the reversible steps come first.

Module 12 answers “what should this be?” This module answers the question you probably have instead: I have X, I need Y, in what order? Each path is graded with the reversibility markers from Module 12, so you can see where you stop being able to change your mind.

Path A — SPA that now needs SEO or first-paint speed

The most common migration, and the one most often attempted backwards.

Step 1 · measureFind out which routes actually need it. Usually it is the marketing pages, the catalogue and a handful of detail pages — not the authenticated application. Migrating the wrong 80% is the standard waste here.
Step 2 · split the surface CheapCarve those routes out as a separate deployment behind a path prefix. Now you can change their rendering without touching the app. This is Module 06's routing-level split used as a migration tool rather than an architecture.
Step 3 · render them on the server CostlyStatic generation if the content changes on a deploy cadence; PPR or ISR if it does not. Keep interactivity as islands. Do not reach for SSR-plus-full-hydration reflexively — if the interactive surface is a search box and an add-to-cart button, hydrating the whole page re-imports the cost you are trying to remove.
Step 4 · leave the app aloneThe authenticated application stays a SPA. That was always the right answer for it.
Trap · The SSR-everything reflex

The instinct is to turn on SSR across the whole application. That gives every route hydration cost and a server render, including the dashboard nobody indexes, and it is how teams end up slower than when they started. SEO is a property of specific routes. Fix those routes.

Path B — monolith splitting across new teams

The path with the most one-way doors, and the one worth going slowest on.

Step 1 · enforce boundaries in place CheapBefore splitting anything, draw the module boundaries inside the existing repo and make them enforced — Nx's lint rule or equivalent. If teams cannot stop importing each other's internals while in one codebase, distributing the deploys will not fix it; it will make the violations invisible.
Step 2 · run it for a quarterThis step is the whole migration. If the boundaries hold, you have found the real seams. If they keep being violated in the same three places, those are not separate domains and you just avoided a very expensive mistake.
Step 3 · split the URL surface CostlyPromote the stable boundaries to routing-level zones behind a proxy. Independent deploys, one full page load when crossing. Stop here unless a screen genuinely needs two teams on it.
Step 4 · only now, runtime composition One-wayFragments or federation, for the specific screens that need it. Everything before this point is reversible. This is not.

Path C — tokens in localStorage to a BFF

Prompted by RFC 10017, and the migration whose ordering matters most, because a half-done version is less secure than either end state.

Step 1 · one origin first CheapProxy all API traffic through the app's own origin. No behaviour change, no auth change — but without it, cookie auth cannot work and you will be tempted to fix that with a Domain cookie, which Module 10 explains is the wrong exit.
Step 2 · stand the BFF up beside the current flow CostlyIt becomes the confidential OAuth client and issues a __Host- session cookie. Both mechanisms work at once. Tokens are still in the browser; nothing has improved yet.
Step 3 · move callers to the cookie sessionRoute by route. The BFF attaches the access token server-side. Instrument which callers still send a bearer token, because that count is your actual progress metric.
Step 4 · cut the browser off One-wayStop issuing tokens to the client, purge storage, and revoke anything outstanding. Only now is the vulnerability closed. Steps 2 and 3 are preparation, not mitigation.
Trap · Never ship steps 2 and 3 with refresh split across both

If the browser still runs its own refresh loop while the BFF also refreshes, you have two clients rotating the same refresh token. Rotation invalidates the other's copy, and users get logged out at random under load — the exact race Module 10 warns about, now with two independent causes. Move refresh ownership to the BFF in a single step, before step 3 begins.

Path D — server-rendered app that needs one genuinely interactive screen

The path where the correct answer is usually “do much less than you were planning.”

Step 1 · try hypermedia Cheaphtmx or Turbo on the existing stack. A surprising share of “we need a SPA for this” screens are a fragment swap and an optimistic update. Contexte went the other direction and removed 67% of their code (Module 02).
Step 2 · if that genuinely fails, one island CheapMount a framework component into the server-rendered page for that screen only. Its own hydration root, its own bundle. The rest of the application never learns about it.
Step 3 · if the island grows into an app CostlyPromote it to its own zone with its own deployment. You are now in Path A's world, deliberately, for one route.

The discipline here is refusing to let step 2 spread. One island is an enhancement; fifteen islands with shared state is a SPA that nobody decided to build and nobody is maintaining as one.

Recap
  • Migrate routes, not applications. SEO and interactivity are route-level properties.
  • Enforce module boundaries before splitting deployments — it is the cheap test for whether your seams are real.
  • In every path, the reversible steps come first and the one-way step comes last. If your plan inverts that, re-order it.
  • A half-migrated auth system is worse than either end state. Move refresh ownership in one step.
  • The most valuable outcome of a migration plan is sometimes discovering you should stop at step 2.
Appendix A

Glossary

Terms of art, defined as they are used in practice rather than as they are marketed.

Acronyms

AJAX
Asynchronous JavaScript and XML. Named by Jesse James Garrett in 2005 for updating part of a page without reloading it. The XML part was obsolete almost immediately; the name stuck.
BCP
Best Current Practice. An IETF document class carrying normative guidance rather than a protocol. RFC 10017 is one.
CDN
Content Delivery Network. Edge caches that serve a response without reaching your server. Whether a rendering mode can use one is the deciding question in Module 06.
CEF
Chromium Embedded Framework. Embeds a Chromium browser in a native application. Spotify's desktop client uses it; Electron is a different wrapper around the same engine.
CGI
Common Gateway Interface (1993). The first standard for a web server to run a program per request rather than serve a file: request metadata arrived as environment variables, the body on stdin, and the response came back on stdout. It made URLs name computations instead of files. It died of forking one OS process per request, and returned as serverless.
CORS
Cross-Origin Resource Sharing. The headers that let a server opt in to being called from another origin. A wildcard origin is rejected when credentials are sent.
CRDT
Conflict-free Replicated Data Type. A data structure whose concurrent edits merge deterministically without a coordinating server. The usual foundation for local-first.
CSR
Client-Side Rendering. The browser builds the HTML from JavaScript. The plain SPA case.
CSRF
Cross-Site Request Forgery. Another site causes the browser to send an authenticated request to yours, using cookies the browser attaches automatically. The cost of cookie sessions; see Module 10.
ESI
Edge Side Includes. Markup that tells a CDN or proxy to fetch a fragment and splice it into a response. Server-side composition, invented for exactly the cacheability problem micro-frontends hit.
IETF
Internet Engineering Task Force. Publishes the RFC series, including the OAuth documents this guide leans on.
ISR
Incremental Static Regeneration. Render once, cache, revalidate in the background on a timer or webhook. Stale-while-revalidate at page level.
MF
Module Federation. Abbreviated this way in its own documentation.
MPA
Multi-Page Application. Every navigation replaces the document, destroying the JavaScript runtime. The default the SPA was defined against — see Module 01.
OWASP
Open Worldwide Application Security Project. Publishes the Cheat Sheet Series, the practical source for the CSRF, session and WebSocket guidance here. CWE is the separate MITRE weakness catalogue.
PKCE
Proof Key for Code Exchange (RFC 7636, said "pixie"). Binds an authorization code to the client that requested it, so an intercepted code cannot be redeemed by anyone else.
PPR
Partial Prerendering. One response carrying a static shell from the CDN plus dynamic holes streamed per request.
PWA
Progressive Web App. Service worker, manifest, offline, installable. Orthogonal to everything on the rendering axis — it describes distribution, not rendering.
RFC
Request for Comments. The IETF's document series. Despite the name, a published RFC is a fixed standards document, not a draft.
RPC
Remote Procedure Call. Calling a function on another machine as if it were local. gRPC and Connect are the current implementations.
RSC
React Server Components. Components that render on the server to a serialized payload and ship no JavaScript. See Module 07.
RTT
Round-Trip Time. Network latency for one request and response. The number that decides whether server-driven interaction feels instant or sluggish.
SEO
Search Engine Optimisation. In this guide it means one thing: can a crawler read your content without executing your JavaScript.
SPA
Single-Page Application. The document loads once and the JavaScript runtime survives every navigation. The definition this guide is built on — see Module 01.
SSE
Server-Sent Events. A one-way stream from server to browser over plain HTTP, with automatic reconnect. Capped at six connections per domain on HTTP/1.1.
SSG
Static Site Generation. HTML produced at build time. Fully cacheable, stale until the next build.
SSI
Server Side Includes. The original directive-based server composition, predating ESI by years.
SSR
Server-Side Rendering. HTML produced by the server rather than the browser — but it is five different things, distinguished in Module 06.
TTFB
Time To First Byte. How long before the response starts arriving. Streaming improves it; blocking on data destroys it.
TTI
Time To Interactive. When the page actually responds to input. The metric hydration cost shows up in.
WHATWG
Web Hypertext Application Technology Working Group. Maintains the HTML Living Standard, which is where import maps and server-sent events are specified.
XSS
Cross-Site Scripting. Attacker-controlled script executing in your origin. The threat every token-storage decision in Module 10 is measured against.

Concepts

bfcache
Back/forward cache. The browser freezes a page's entire JS heap on navigation away and thaws it on return, making back-navigation instant. Disqualified by an unload handler or Cache-Control: no-store. Does not apply to SPA soft navigations.
BFF
Backend for Frontend. A backend owned by and shaped for one frontend. In RFC 10017 it specifically means a confidential OAuth client that holds tokens server-side and proxies all API traffic, exposing only a cookie session to the browser.
CHIPS
Cookies Having Independent Partitioned State. A cookie marked Partitioned is double-keyed on both the setting origin and the top-level site, so an embedded widget gets separate state per embedding site.
CSWSH
Cross-Site WebSocket Hijacking. Because browsers attach cookies to WebSocket handshakes and do not apply CORS to them, a malicious site can open an authenticated socket to your server unless you validate Origin.
Cacheability floor
A composed page is only as cacheable as its least cacheable fragment. One team's per-user fragment makes the whole document uncacheable at the CDN unless the composition layer caches per fragment.
One-way door
A decision whose reversal costs a rewrite rather than a refactor. Micro-frontends, auth architecture and local-first are the three in this guide; see Module 12.
Selective SSR
Not a standard term. Used for three different things: per-route rendering choice, partial prerendering within one page, or React's selective hydration. Establish which is meant before agreeing to anything.
Share scope
Module Federation's runtime namespace of shared dependencies. Each build registers what it has and consumers take the highest version satisfying their requirement — unless singleton forces one instance.
Hashbang (#!)
A URL fragment beginning with !, used by pre-2012 SPAs because the fragment was the only part of the URL writable without triggering a page load. Google's 2009 crawling scheme gave it special meaning so crawlers could request a server-rendered snapshot; deprecated 2015, obsoleted by pushState.
Hydration
Attaching a client-side framework to server-rendered HTML so it becomes interactive, reusing the existing DOM rather than rebuilding it.
Hypermedia-driven
An architecture where the server returns HTML fragments the client swaps into the existing document — SPA-like responsiveness with server-owned state. htmx, Turbo, Unpoly.
Islands architecture
Mostly-static server-rendered HTML with small, independently hydrated interactive regions. Coined by Katie Sylor-Miller (2019), popularised by Jason Miller (2020) and Astro.
Local-first
The client holds the authoritative copy of data in local storage (IndexedDB, SQLite-wasm) and syncs to the server opportunistically. Usually built on CRDTs or a sync engine.
Module Federation
A bundler feature allowing one build to load modules from another build at runtime, with negotiated sharing of common dependencies. Originated in webpack 5; now an independent project supporting several bundlers.
Multi-Zones
Next.js's name for routing-level composition: several independent applications each owning a set of URL paths behind one domain. Navigation within a zone is soft; between zones it is a full page load.
Out-of-order streaming
Sending HTML for later parts of a page before earlier parts are ready, appending them as hidden blocks and relocating them with a small inline script.
Podlet / Layout
Podium's terms: a podlet serves one page fragment as a service; a layout composes podlets into a finished page and supplies each with context headers.
Runtime lifetime
How long one JavaScript execution context — global object, heap, module registry, event-loop registrations — survives. The property that actually distinguishes SPA from MPA.
Shell (React streaming)
The part of a React tree outside any <Suspense> boundary — the HTML that must be ready before streaming can begin.
Shell (micro-frontends)
The host application that owns routing, layout and cross-cutting concerns, into which micro-frontends are mounted. Also called the container or orchestrator.
Singleton (federation)
A shared dependency constrained to exactly one instance across all federated builds. Required for libraries with global internal state, such as React.
Subgraph / Supergraph
Apollo Federation's terms: subgraphs are the constituent GraphQL APIs; the supergraph is the composed graph; the router is the client-facing entry point that distributes requests.
Version skew
A client running an older deployed bundle against a newer backend, or two micro-frontends running mutually incompatible versions of a shared library. The dominant failure mode of non-atomic deployment.

Corrections to earlier drafts of this material

These were stated confidently and were wrong. They are recorded because the direction of each error is instructive.

  • “Tailor is the reference implementation of fragment streaming.” It was archived in December 2022. The pattern is alive; that implementation is not. Lesson: architecture patterns outlive their reference implementations, and citations rot silently.
  • “Use HttpOnly cookies on a shared parent domain.” RFC 10017 says The BFF SHOULD NOT set the Domain attribute for cookies. The cookie-over-token advice was right; the scoping advice was wrong, and the correct design makes parent-domain scoping unnecessary. Lesson: a plausible mechanism is not a substitute for reading the current BCP.
  • “Escalate to Module Federation when you need seamless composition” — stated without caveats. Next.js federation is deprecated and Turbopack cannot run webpack plugins. The advice holds for Rspack and Vite; on Next.js it is a dead end. Lesson: general architectural advice needs a per-stack feasibility check.
  • “React requires a single copy across federated boundaries.” Overstated. React permits multiple independent copies; it breaks only when react resolves differently for a component and the react-dom that rendered it. Lesson: the precise condition is more useful than the safe generalisation, because it tells you which designs are actually available.
  • “MPAs can now feel like SPAs” via View Transitions — true in Chromium and Safari, not in Firefox. Lesson: “the platform can do this now” usually means “most of the platform can.”

Appendix D

When this guide is wrong

The strongest cases against this guide's main positions, made as their defenders would make them.

Every recommendation here has a defensible opposite. If your situation matches one of these, the guide's default is the wrong answer for you and you should be able to say why.

“Routing-level zones by default”

The case against: zones are an admission of defeat on the actual problem. If your product is one coherent application — a shared left nav, a persistent player, a cart that must never lose state — a full page load at every boundary is a visible product regression that users feel and you will be asked to fix. At that point you build a shell to preserve state across zones, and you have arrived at runtime composition anyway, having paid twice. Teams that went straight to Module Federation got one integration problem instead of two.

When they are right: when boundaries fall inside a single continuous workflow rather than between them. Test it by asking what must survive a boundary crossing. If the honest answer is “a media player, an open draft, and a cart,” zones will fight you.

“Never put tokens in the browser”

The case against: a BFF is a stateful, always-on service on the critical path of every request — something to deploy, scale, monitor, and page someone about. For a small team shipping a low-sensitivity product, that operational cost is real and the threat it mitigates is not: if an attacker is executing script in your origin, they can drive the session through the BFF regardless. You have bought protection against token exfiltration and replay elsewhere, which is narrower than it first appears.

When they are right: low-sensitivity data, short sessions, narrowly-scoped tokens, a small team with no platform capacity. Note that RFC 10017 anticipates this — it reserves its strongest language for business applications, sensitive applications, and applications that handle personal data. If you are none of those, the BCP is not addressed to you.

“Runtime lifetime is the dividing line”

The case against: this is the guide's own framing and it is a choice, not a fact. You could organise the same territory by who owns the data, or by what the network boundary costs, and get different and equally coherent groupings. The runtime framing makes LiveView look exotic when it is a straightforward client-server terminal, and it undersells how much of the real difficulty is cache invalidation rather than lifetime.

Why it is still used here: it predicts the most downstream consequences from one property. That is a claim about usefulness, not truth.

“Micro-frontends only for independent deployment”

The case against: build time is a real engineering cost and at some scale it dominates everything else. A twenty-minute CI run changes how often people refactor, which changes the code. Splitting for build performance alone — without any deploy independence — is a legitimate use that this guide and Nx both dismiss slightly too quickly.

The counter: remote caching and affected-task graphs (Module 11) usually solve build time at a fraction of the cost. Try those first, then re-measure.

“Next.js federation is a dead end”

The case against: deprecated is not the same as broken. Pages Router plus NEXT_PRIVATE_LOCAL_WEBPACK still works, and for a team already there, a working deprecated setup can outlast a migration that competes with product work. “Do not start here” and “rip out what you have” are different recommendations and the guide runs them together.

The limit: you are pinned below Next.js 16 and off the App Router permanently. Treat it as a deliberate freeze with an exit date, not as a supported position.

“The best shared state is no shared state”

The case against: pushed far enough this produces its own pathology — six teams each fetching /me, six near-identical cart representations, and cross-cutting concerns smeared across boundaries because nobody was allowed to own them. A small, explicitly-owned shared store is sometimes simply correct, and the URL cannot carry everything.

Where the line actually is: shared reads are cheap and usually fine. Shared writes are what couples teams. The principle is really about mutation, and the guide states it more absolutely than that.

If you are about to depart from one of this guide's defaults, the relevant section above is the argument you will need to make to your team — and the conditions listed are the ones you should be able to point at.
