<Insight title="Start here or waste a year">
Micro-frontends solve exactly one problem: **N teams need to deploy independently onto one URL surface.** They are Conway's law (Melvin Conway, 1967) expressed as a build system.

Three teams and one deploy pipeline? You do not have this problem. Do not pay the cost.
</Insight>

<Source>
<Quote>If your teams can deploy together and you mainly want faster builds, runtime composition is the wrong tool for that problem.</Quote>

<Cite>— [Nx, Micro Frontend Architecture](https://nx.dev/docs/kb/micro-frontend-architecture)</Cite>
</Source>

#### And the answer changes with team count

This guide otherwise speaks as if there is one answer. There is not — the same architecture is wrong at one scale and necessary at another.

| Teams on the surface | What is usually right |
| --- | --- |
| **1–3** | A modular monolith. Enforced module boundaries (<Mod to="delivery" />) give you most of the discipline with none of the runtime cost. Micro-frontends here are almost always a mistake. |
| **4–8** | Routing-level zones. Real deploy independence, boring failure modes, no platform team required. |
| **9–20** | Zones plus fragment composition where teams genuinely share a screen. You now need someone to own the shell contract full-time. |
| **20+** | A platform team is not optional — version negotiation, the shell, the deploy pipeline and the governance become somebody's actual job. This is the scale the published case studies later in this module are drawn from. |

Reading a Zalando or Amex writeup at four teams is the most common way this architecture gets adopted for the wrong reasons.

### Where you compose

The real taxonomy is not “which framework” but “at what point in the pipeline do the pieces become one page.” The canonical treatment is [Cam Jackson's article on martinfowler.com](https://martinfowler.com/articles/micro-frontends.html), covering server-side template composition, build-time integration, and run-time integration via iframes, JavaScript and Web Components.

| Composition point | Mechanism | Independent deploy | SEO / first paint | Isolation | Cost |
| --- | --- | --- | --- | --- | --- |
| Build time | npm packages, shell imports them | <No>No</No> | <Ok>Good</Ok> | Weak | Low |
| Server side | Podium, Multi-Zones, SSI/ESI | <Ok>Yes</Ok> | <Ok>Best</Ok> | Good | Medium |
| Edge | ESI at CDN, Workers streaming | <Ok>Yes</Ok> | <Ok>Good</Ok> | Good | Medium |
| Runtime — iframe | `<iframe>` | <Ok>Yes</Ok> | <No>Poor</No> | <Ok>Strongest</Ok> | UX pain |
| Runtime — web components | Custom Elements + Shadow DOM | <Ok>Yes</Ok> | Partial | Real CSS isolation | Medium |
| Runtime — Module Federation | webpack / Rspack / Vite | <Ok>Yes</Ok> | Needs SSR work | <No>Weak — shared graph</No> | High |
| Runtime — orchestrator | single-spa + import maps | <Ok>Yes</Ok> | Needs SSR work | Weak | Medium |

<Insight title="The tension you cannot escape">
**The more seamless your UX integration, the more coupled your dependency graph.**

Iframes: perfectly independent, unpleasant to use. A federated single React tree: seamless, and every team is now on one React version. No configuration gives you both.

Choose which pain you accept — deliberately, not in month eight.
</Insight>

It is worth noting that the other canonical reference takes the opposite side of this trade. [Michael Geers' micro-frontends.org](https://micro-frontends.org/) lists among its core principles: <q>Isolate Team Code — Don't share a runtime, even if all teams use the same framework.</q> and <q>Build a Resilient Site — Your feature should be useful, even if JavaScript failed or hasn't executed yet.</q> Both positions are defensible. Know that you are picking a side.

<Moved title="The abandonment case">
Spotify's old desktop client was a micro-frontend architecture — <q>every 'page' in the client was built as a standalone 'app' to run inside its own iframe. **This architecture was designed to foster autonomy.**</q>

They removed it. From the same post: <q>Eventually, however, one team became responsible for the user interface of the entire application</q> and <q>this architecture was causing severe friction for developers</q> — they <q>were not shipping new features at the pace we would have liked to.</q> The replacement is a single shared React codebase across desktop and web.

Read that first sentence against the rule at the top of this module. The architecture was built for team autonomy; when the org changed and one team owned the UI, the justification disappeared and only the cost remained. **Micro-frontends are indexed to your org chart, and org charts change.**

<Cite>— [Spotify Engineering, "Building the future of our desktop apps"](https://engineering.atspotify.com/2021/04/building-the-future-of-our-desktop-apps)</Cite>
</Moved>

### “SSR” is five different things

Before the composition patterns, the modes need separating — because they behave very differently once more than one team is involved. The question that distinguishes them is **when the HTML is produced**, and the consequence that matters is **whether a CDN can cache it**.

| Mode | HTML produced | CDN-cacheable | Freshness |
| --- | --- | --- | --- |
| **Static generation** | At build | <Ok>Fully</Ok> | <No>Stale until you rebuild</No> |
| **Request-time SSR** | Per request | <No>No</No> | <Ok>Always fresh</Ok> |
| **On-demand / ISR** | First request or webhook, then cached and revalidated in the background | <Ok>Yes</Ok> | Stale-while-revalidate |
| **Streaming SSR** | Per request, flushed progressively | <No>Not as one unit</No> | <Ok>Fresh, much better TTFB</Ok> |
| **Partial prerendering** | Static shell at build + dynamic holes streamed per request | <Warn>Shell yes, holes no</Warn> | <Ok>Fresh where it matters</Ok> |

The last one is the newest and is no longer experimental.

<Source>
<Quote>This rendering approach is called **Partial Prerendering (PPR)**, the default behavior with Cache Components.</Quote>

And the mechanism, which is exactly the streaming sequence from <Mod to="streaming" /> applied at build boundaries: <q>Every produced static shell can be served directly from a CDN, without going through to the upstream server.</q> Components marked `'use cache'` join the shell; anything wrapped in `<Suspense>` streams at request time.

<Cite>— [Next.js, Caching with Cache Components](https://nextjs.org/docs/app/getting-started/caching), docs v16.3.5. Cache Components shipped in 16.0.0 and is enabled with `cacheComponents: true`.</Cite>
</Source>

<Trap title="“Selective SSR” means three different things">
It is not a standard term, and people use it for at least three unrelated mechanisms. Establish which one is meant before agreeing to anything:

1. **Per-route rendering choice** — some routes server-rendered, others static or client-only. The most common meaning, entirely standard, and every meta-framework has it: Next.js route segment config, Nuxt `routeRules`, SvelteKit's `export const ssr = false`. Nothing exotic.
2. **Partial prerendering** — selective *within one page*: a static shell plus dynamic holes, in one response. This is what PPR above is.
3. **Selective hydration** — React's term, and not an SSR mode at all. It is about which parts get JavaScript and in what order (<Mod to="streaming" />). Routinely conflated with the other two because the word is the same.

All three are current and widely used. They solve different problems, and a conversation where one person means (1) and the other means (3) will appear to agree and then produce the wrong architecture.
</Trap>

#### Which modes survive composition

This is the part that is absent from most micro-frontend writing, and it is where the real constraint lives:

<Insight title="The cacheability floor">
**A composed page is only as cacheable as its least cacheable fragment.**

One team's per-user fragment makes the whole assembled document uncacheable at the CDN — unless the composition layer caches each fragment separately. That single property decides which composition pattern you can afford.
</Insight>

| Composition pattern | What happens to the SSR modes |
| --- | --- |
| **Routing-level zones** | <Ok>All five survive, independently. Each zone is a whole application with its own cache policy — team A can be fully static, team B can run PPR, and neither constrains the other. This is the strongest argument for zones that nobody makes.</Ok> |
| **Server fragment composition** | Survives, but you must do the work. Every fragment needs its own TTL and the layout must honour it — this is precisely what ESI was invented for, and what Podium's manifest and context headers carry. Streaming is the natural fit. The trap: fragments then have *different ages* on one page, which is fine for nav and footer and dangerous for price next to stock level. |
| **Federated SSR** | <No>Mostly collapses. One render, one response, one cache policy. ISR and PPR both assume a single build knows which parts are dynamic, and a remote that decides at runtime breaks that assumption. In practice you fall back to request-time SSR for the whole page, losing the CDN entirely.</No> |

<Trap title="Crawlers take a different code path">
Under PPR, bots do not get the cached shell. From the same docs: <q>because they need a complete document, Next.js skips the shell and renders the entire page dynamically at request time.</q>

So your SEO traffic exercises a different rendering path from your users, and <q>work that completed during prerendering now runs at request time for a bot.</q> A page that loads fine for a person can fail for a crawler if the shell depended on build-time data. In a composed page, that failure mode is multiplied by the number of teams contributing to the shell.
</Trap>

### SSR with micro-frontends: three patterns

#### 1. Fragment services — when SEO and first paint matter

Each micro-frontend exposes an HTTP endpoint returning an HTML fragment plus its asset manifest. A layout service fetches them in parallel and streams them into one document as they arrive. <Mod to="streaming" /> covers the mechanics.

#### 2. Routing-level split — the pragmatic default

Each micro-frontend owns a URL prefix and is a complete, independent application behind a reverse proxy. [Next.js formalises this as Multi-Zones](https://nextjs.org/docs/app/guides/multi-zones); plain Nginx does it too.

<Source>
<p><q>Multi-Zones are an approach to micro-frontends that separate a large application on a domain into smaller Next.js applications that each serve a set of paths.</q> … <q>Since applications are decoupled, Multi-Zones also allows other applications on the domain to use their own choice of framework.</q></p>

And the behaviour you must design around: <q>Navigating between pages in the same zone will perform soft navigations… Navigating from a page in one zone to a page in another zone… will perform a hard navigation.</q> Consequently, <q>Links to paths in a different zone should use an `a` tag instead of the Next.js `<Link>` component.</q>

<Cite>— [Next.js, Multi-Zones](https://nextjs.org/docs/app/guides/multi-zones)</Cite>
</Source>

This is an MPA of SPAs, and it is dramatically more robust than the alternatives: no shared bundler configuration, no runtime version negotiation, independent failure domains. The cost is one full page load when crossing a zone boundary. Speculation rules can prerender the next zone so the load is fast everywhere they are supported; cross-document View Transitions smooth the swap in Chromium and Safari but not yet in Firefox (<Mod to="navigation" />). Design for the hard navigation and treat the smoothness as an enhancement.

<Insight title="What “the shell” means once you have zones">
A zone crossing is a document replacement, so by <Mod to="dividing-line" />'s definition **nothing in memory survives it** — no shell runtime, no open socket, no in-memory store. With zones, "the shell" is not a running program; it is a **shared layout package** (header, nav, tokens, the session client) that every zone renders, plus a contract for what must survive a crossing.

That contract has exactly three carriers: the **URL**, **cookies** (the BFF session, <Mod to="auth" />) and **browser storage**. Anything else — a media player, an unsent draft — either lives inside one zone or is the signal that the boundary is in the wrong place (<Mod to="counter" />).

Two rules from later modules change shape accordingly. *One owner for history* becomes one router **per document**: each zone's router owns the address bar while it is loaded, and cross-zone links are plain `<a>` tags. *One realtime connection* becomes one **per tab**, re-established on every zone load — or, if reconnect cost matters, one per browser held by a `SharedWorker` or a `BroadcastChannel` leader tab (<Mod to="transports" />).
</Insight>

#### 3. Federated SSR — most seamless, most operationally expensive

The host imports remote modules over the network at request time and renders everything into one tree. Your server render now has a network fan-out on the critical path, so you need remote-entry caching, version pinning, and a degraded mode for every remote. It works. It is not where you start.

### Specifically in Next.js

Worth its own treatment, because Next.js is where most teams ask this question and because the options divide cleanly into **build-time** (one deployable, no independent release) and **runtime** (separately deployed, assembled when a request arrives). Teams routinely believe they have the second and have built the first.

| Mechanism | When composed | Independent deploy | App Router | Status |
| --- | --- | --- | --- | --- |
| **Workspace packages**<Sub>shared UI imported by the shell</Sub> | Build | <No>No</No> | <Ok>Yes</Ok> | Fine — just not micro-frontends |
| **Turborepo / Nx orchestration** | Build | <Ok>Yes, per app</Ok> | <Ok>Yes</Ok> | Each app is still whole; this is delivery, not composition |
| **[Multi-Zones](https://nextjs.org/docs/app/guides/multi-zones)** | Runtime, routing | <Ok>Yes</Ok> | <Ok>Yes</Ok> | <Ok>Framework-native. The default answer.</Ok> |
| **[Vercel Microfrontends](https://vercel.com/docs/microfrontends)** | Runtime, routing at the network layer | <Ok>Yes</Ok> | <Ok>Yes</Ok> | <Ok>Generally available; each app is its own project</Ok> |
| **Your own reverse proxy**<Sub>Nginx, Cloudflare, ALB</Sub> | Runtime, routing | <Ok>Yes</Ok> | <Ok>Yes</Ok> | <Ok>Same shape, no vendor coupling</Ok> |
| **Server-side fetch in an RSC** | Runtime, server | <Ok>Yes</Ok> | <Ok>Yes</Ok> | Underused — see below |
| **iframes / Web Components** | Runtime, browser | <Ok>Yes</Ok> | <Ok>Yes</Ok> | Framework-agnostic, unaffected by any of this |
| **Module Federation** | Runtime, module | <Ok>Yes</Ok> | <No>Never supported</No> | <No>Deprecated, and Turbopack cannot load the plugin</No> |

**The RSC row is the interesting one.** A server component can simply `await fetch()` another team's endpoint and render the result into its own tree — which is server-side fragment composition without a composition framework, using nothing but the language. It gets you independent deploys and no shared client runtime. What it does not get you is the fragment contract that Podium's manifest provides: you own the timeouts, the fallbacks, the caching and the versioning yourself, and there is nothing stopping a fragment's shape from changing underneath you.

<Trap title="Build-time composition sold as micro-frontends">
Extracting shared components into a workspace package feels like splitting the frontend. It is not. Every consumer still has to rebuild and redeploy to pick up a change, so you have added a versioning step and gained nothing on release independence.

The test is one question: **can one team ship a user-visible change without any other team's pipeline running?** If no, it is a modular monolith — which is often the right answer (<Mod to="delivery" />), but should be called by its name so nobody budgets for the wrong thing.
</Trap>

### CSS and the design system

The problem nobody plans for and everybody hits in month two: independently deployed teams producing one visual surface. It is harder than shared state, because CSS has no module system and no versioning — the cascade is a single global namespace that every team writes into at runtime.

| Approach | Isolation | The catch |
| --- | --- | --- |
| Global stylesheet, shared | <No>None</No> | One team's `.button` restyles another's. Works only with strict naming discipline nobody sustains. |
| CSS Modules / scoped styles | <Ok>Good</Ok> | Hashed class names, so collisions are gone. Global resets still collide. |
| CSS-in-JS | <Ok>Good</Ok> | Runtime cost, and each micro-frontend ships its own copy of the library. |
| Utility framework (Tailwind) | <Warn>Partial</Warn> | Each team compiles its own subset — duplicated but non-conflicting. **Different major versions collide on the preflight reset**, which is a real and confusing failure. |
| Shadow DOM | <Ok>Total</Ok> | Nothing leaks in or out — including your design system. See below. |

#### The versioning trap

A shared design-system package looks like the obvious answer and quietly reintroduces the coupling the architecture was meant to remove. Pin it per team and they drift visually until a redesign requires eight coordinated releases. Force one version and you have build-time coupling — every design change means every team rebuilds and redeploys.

<Insight title="Split tokens from components">
**Ship design tokens at runtime; ship components at build time.**

Tokens — colour, spacing, type scale, radius — go out as CSS custom properties served by the shell. Change a brand colour centrally and every micro-frontend picks it up on next load, with nobody redeploying.

Components stay a versioned package each team upgrades on its own schedule. A team lagging two versions looks slightly dated; it does not look like a different product, because the tokens underneath are current.

And the detail that makes this work with Shadow DOM: **custom properties inherit through shadow boundaries** where stylesheets do not. Tokens are the one thing that can cross the isolation you just paid for.
</Insight>

Two operational rules worth adopting early. **Prefix everything** — class names, custom element names, CSS custom properties, `localStorage` keys — with the owning team's name; this is one of the core practices on [micro-frontends.org](https://micro-frontends.org/) and costs nothing to start with and a great deal to retrofit. And **one team owns global CSS**: resets, `@font-face`, `:root` tokens, and nothing else is allowed at document scope.

### Sharing state: a ranked ladder

<Insight title="The governing principle">
**The best shared state is no shared state.** (Not original here — a common formulation in the field.)

If two micro-frontends share a lot of *mutable* state, they are not two micro-frontends. You drew the boundary along screen regions instead of business domains. Redraw it before picking a mechanism.
</Insight>

1. **The URL.** Wildly underrated and almost always sufficient. Selected entity, filters, active tab, pagination, sort order. Zero coupling, no library, survives reload, deep-linkable, and the browser maintains it for you. Exhaust this before anything else.
2. **Server state, not client state.** Most “shared state” is cached server data in disguise. Two micro-frontends that both need the cart count should both ask the API, backed by a shared HTTP cache (ETag, `Cache-Control`) or one shared query-client instance. *Reframing shared state as shared cache is the single biggest lever available to you.*
3. **Events.** `CustomEvent` on `window`; `BroadcastChannel` for cross-tab and cross-iframe. Version the contracts (`cart:item-added@v1`).
4. **One small shell-owned singleton.** Not a global Redux store — a deliberately tiny, versioned contract for what is genuinely cross-cutting: auth/session, theme, locale, feature flags, notifications. That list is close to complete.
5. **Props down, events up**, if your micro-frontends are custom elements. It is just the DOM contract, and it is the cleanest boundary available.
6. **Web storage** for tokens and preferences only. A poor reactive store: no same-tab event, strings only, quota limits.

<Trap title="Events are not state">
A micro-frontend that mounts *after* an event fired never sees it, and will render with stale or empty data. This produces bugs that only appear under specific navigation orders and are miserable to reproduce.

Always pair a broadcast with a “read the current value” accessor. The event says *something changed*; the accessor answers *what is it now*.
</Trap>

**Anti-patterns worth naming:** a shared global Redux store (you rebuilt the monolith, then distributed its deploys); importing another micro-frontend's internals; and passing React context across a federated boundary where React is not a singleton — see <Mod to="federation" />.

<Recap>
- Micro-frontends solve independent deployment for many teams. Nothing else. If that is not your problem, stop.
- Composition point is the real taxonomy: build-time, server, edge, or runtime.
- Seamlessness and decoupling trade against each other directly. Choose deliberately.
- Routing-level split is the pragmatic default; fragment streaming when SEO demands it; federated SSR last.
- The state ladder starts at the URL and at treating shared state as shared cache.
</Recap>
