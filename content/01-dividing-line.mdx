A SPA is usually described by three traits: one HTML file, client-side routing and no page reload. Those traits are effects of something else.

<Insight title="The core distinction">
The dividing line is **what an interaction does to the JavaScript runtime.**

**Server-rendered:** every interaction replaces the document. The browser throws away the JavaScript heap, every variable and every closure. It also throws away the DOM, the tree of elements on the page. Then it builds everything again from zero.

**SPA:** the document loads once and the runtime **stays alive**. Navigation is a function call: it swaps components, pushes a new URL and keeps everything else.
</Insight>

Bundle size, SEO difficulty, hydration, API design and cache invalidation all follow from runtime lifetime. So does whether you need a client-side router at all. Two definitions make runtime lifetime precise:

- **The runtime:** the global object, the JavaScript heap, the module registry and everything registered on the event loop. The heap is the memory that holds every object. The module registry holds every module already loaded. The event loop runs timers, listeners and other callbacks.
- **What ends it:** a full document navigation, a hard reload, a crash, or a phone discarding a background tab when memory runs low.

### Runtime lifetime and state lifetime are separate

An MPA has a *short* runtime and *long-lived* state. The state lives in a server session, found again on each request through a cookie. So the application keeps state, but the browser does not. Because the state does not depend on the runtime, MPAs have worked for two decades and still do.

Once you separate the two lifetimes, the architectures below stop looking like a line from primitive to modern. Each one gives a different answer to the same question: **where does the long-lived state live, and who can change it?**

| Architecture | Runtime lives for | Long-lived state sits in | Typical problem |
| --- | --- | --- | --- |
| Static documents | — | URL, cookies | None. This is the easy case. |
| Classic MPA | One document | Server session | Client state is lost on every click |
| MPA + AJAX | One document | Server session, plus JavaScript scoped to the page | Widget state is lost on navigation |
| htmx / Turbo | **Long**: the document stays, parts of the DOM are swapped | Server. The DOM *is* the client state | Timers and listeners outlive their elements |
| LiveView / Blazor Server | **Long, but on the server** | Server memory, one process or circuit per connection | Server memory grows with users connected at once. Each event the server handles costs a round trip |
| SPA (CSR) | Whole session | Client memory | Memory leaks, version skew, tabs discarded in the background |
| SSR + hydration | **Two**: one per request on the server, then a long one on the client | Client, after hydration | State in a server module's scope is shared between users |
| Static generation | Build time, then the client session | Client | Pages go out of date |
| Islands | **One per island**, independent of each other | Each island | Islands cannot see each other's state |
| Server Components | One per request on the server, plus a long one on the client | Client components only | Newer, less settled tooling |
| Local-first | **Longer than the session** | The device | Keeping tabs in sync, resolving conflicting edits |

### Three cases the table oversimplifies

#### htmx and Turbo: the runtime survives each swap, but the elements do not

htmx and Turbo keep one document open and swap in HTML fragments from the server. So the JavaScript runtime survives each swap. Each swap throws away the elements it replaces and inserts new ones.

Code written for the old elements does not stop on its own. A `setInterval` timer keeps firing after its element is removed. A listener on `window` or `document` stays registered. Teams read "no client state" as "no lifecycle to manage". That is wrong, and both tools give you a hook to clean up:

- **Turbo** is part of [Hotwire](https://hotwired.dev/), which pairs it with Stimulus, a small library for the custom JavaScript Turbo does not cover. A Stimulus controller's `disconnect()` runs [whenever the controller is disconnected from the DOM](https://stimulus.hotwired.dev/reference/lifecycle-callbacks).
- **htmx** fires `htmx:beforeCleanupElement` [before it disables an element or removes it from the DOM](https://htmx.org/events/#htmx:beforeCleanupElement).

In htmx, start the timer when htmx loads new content, and clear it before htmx removes the element. The example below uses the documented [`htmx.onLoad()`](https://htmx.org/api/#onLoad), [`htmx.on()`](https://htmx.org/api/#on) and `htmx:beforeCleanupElement`. Without its last 3 lines, every swap leaves the old clock's timer running. On a page that starts with no clock, 5 swaps leave 5 timers running but only 1 clock on screen.

```js file="app.js" label="htmx: clear the timer before the element is removed"
const timers = new WeakMap();

htmx.onLoad((content) => {
  const clocks = [content, ...content.querySelectorAll('[data-clock]')]
    .filter((el) => el.matches('[data-clock]'));
  for (const el of clocks) {
    timers.set(el, setInterval(() => {
      el.textContent = new Date().toLocaleTimeString();
    }, 1000));
  }
});

htmx.on('htmx:beforeCleanupElement', (evt) => {
  clearInterval(timers.get(evt.detail.elt));
});
```

In Stimulus, `connect()` starts the timer and `disconnect()` clears it. This controller comes from the [Stimulus handbook](https://stimulus.hotwired.dev/handbook/working-with-external-resources#releasing-tracked-resources). It reloads a piece of HTML at an interval set in its HTML attributes, such as every 5 seconds.

```js file="src/controllers/content_loader_controller.js" label="Stimulus: disconnect() clears the timer"
import { Controller } from "@hotwired/stimulus"

export default class extends Controller {
  static values = { url: String, refreshInterval: Number }

  connect() {
    this.load()

    if (this.hasRefreshIntervalValue) {
      this.startRefreshing()
    }
  }

  disconnect() {
    this.stopRefreshing()
  }

  load() {
    fetch(this.urlValue)
      .then(response => response.text())
      .then(html => this.element.innerHTML = html)
  }

  startRefreshing() {
    this.refreshTimer = setInterval(() => {
      this.load()
    }, this.refreshIntervalValue)
  }

  stopRefreshing() {
    if (this.refreshTimer) {
      clearInterval(this.refreshTimer)
    }
  }
}
```

#### LiveView and Blazor Server: live state on the server for every open page

These are not a point between SPA and MPA. They are a third model:

- The long-lived state stays in server memory, not in the browser.
- In LiveView, the browser keeps a WebSocket open to the server. A WebSocket is a connection that stays open, so either side can send at any time. On the server, <q>LiveViews are processes that receive events, update their state, and render updates to a page as diffs.</q> ([Phoenix LiveView](https://phoenix-live-view.hexdocs.pm/welcome.html))
- In Blazor Server, <q>the state on the server associated with each connected client is called a *circuit*.</q> Each browser tab needs its own circuit. ([Microsoft, Blazor hosting models](https://learn.microsoft.com/en-us/aspnet/core/blazor/hosting-models))
- The browser only applies the page changes the server sends.

Latency is the time a message takes to reach the server and come back, a round trip. This model works well when latency is low. At a 200 ms round trip it feels slow, because each event the server handles waits for that round trip. Microsoft says the same of Blazor Server: <q>Every user interaction involves a network hop.</q> ([Blazor hosting models](https://learn.microsoft.com/en-us/aspnet/core/blazor/hosting-models)) Server memory also grows with the number of users connected at once, not with how many requests arrive per second.

#### bfcache: an MPA's runtime can survive a navigation

bfcache is the browser's [back/forward cache](https://web.dev/articles/bfcache). When you leave a page, the browser can freeze its whole JavaScript heap. When you come back with Back or Forward, it restores the heap as it was. So even an MPA's runtime can outlive a navigation. <Mod to="navigation" /> lists the two things that silently stop your page from using it.

### Is a SPA only possible in a browser?

The answer has two parts.

**Yes, in one sense.** "SPA" only means something in contrast to the browser's default, which replaces the document on every navigation. On a platform without that default, the term has nothing to contrast with. Nobody calls an iOS app a single-page application. Every native GUI app already works that way.

**No, in another.** A SPA needs a browser *engine*, not a browser *tab*. Electron, Tauri, Capacitor, WKWebView and Android WebView all provide one. [VS Code](https://code.visualstudio.com/docs/editor/whyvscode) and [Slack](https://slack.engineering/building-hybrid-applications-with-electron/) run on Electron. [Spotify's desktop client uses CEF](https://engineering.atspotify.com/2021/04/building-the-future-of-our-desktop-apps). All three are SPAs running in an embedded browser inside a native window.

<Insight title="The SPA is the normal model">
The SPA is not an innovation. It brings the web back to the model that GUI apps always had: a runtime that stays alive, state in memory, and an event loop. Smalltalk, Win32 and Cocoa worked this way from the start.

The **MPA** is the exception. It destroys and rebuilds the whole UI after every click. It exists only because the web began as a system for linked documents and was later used as an app platform.
</Insight>

<Recap>
- What separates a SPA from an MPA is runtime lifetime, not page count. Replacing the document destroys the JavaScript heap. SPA navigation does not.
- Runtime lifetime and state lifetime are separate. MPAs have long-lived state too: it lives on the server.
- Long-lived state on the *server*, held per connection, is a third model. It is not a midpoint between SPA and MPA.
- A SPA needs a browser engine, not a browser tab. It follows the normal GUI model; the MPA is the exception.
</Recap>
