[**RFC 10017, “OAuth 2.0 for Browser-Based Applications”**](https://www.rfc-editor.org/info/rfc10017/) was published on **21 August 2026** as a Best Current Practice. It sits in [BCP 212](https://www.rfc-editor.org/info/bcp212/) alongside [RFC 8252](https://www.rfc-editor.org/info/rfc8252/) (native apps) — worth stating because BCP numbers can contain several RFCs and this is easy to get wrong.

### Three architectures, ranked by the RFC itself

<Source title="Pattern 1, BFF">
<Quote>A browser-based application that relies on a backend component for handling OAuth responsibilities and forwards all requests through the backend component ('Backend for Frontend' or 'BFF').</Quote>

Its three responsibilities: act as a confidential OAuth client; <q>manage OAuth access and refresh tokens in the context of a cookie-based session, avoiding the direct exposure of any tokens to the browser-based application</q>; and forward all requests to resource servers, <q>augmenting them with the correct access token.</q>

Verdict: <q>This architecture is strongly recommended for business applications, sensitive applications, and applications that handle personal data.</q>

<Cite>— [RFC 10017 §6.1](https://www.rfc-editor.org/info/rfc10017/)</Cite>
</Source>

**Pattern 2, token-mediating backend:** the backend does OAuth but the browser calls resource servers directly with the token. <q>From a security perspective, the token-mediating backend is less secure than a BFF but still offers significant advantages over an OAuth client application running directly in the browser.</q>

**Pattern 3, browser-based OAuth client:** everything in the browser. <q>If an attacker is able to execute malicious code in the browser, this application architecture is vulnerable to all attack scenarios discussed earlier… This architecture is not recommended for business applications, sensitive applications, and applications that handle personal data.</q>

### The three, as request flows

The whole difference is one question: **does an access token ever exist inside the browser?** The boxes flagged *token here* are where it does.

#### 1 — BFF · strongly recommended

<Flow>
<Box kind="good" title="Browser">Holds a cookie. Never sees a token.</Box>
<Arrow>session cookie<br />HttpOnly, Strict</Arrow>
<Box kind="good" title="BFF">Confidential client. Holds access + refresh tokens server-side.</Box>
<Arrow>Bearer token<br />attached here</Arrow>
<Box title="Resource server">Your API</Box>
</Flow>

<FlowCaption>The BFF also talks to the authorisation server, as a confidential client. An XSS in the browser can make requests *through* the session, but cannot steal a token to replay elsewhere.</FlowCaption>

#### 2 — Token-mediating backend

<Flow>
<Box kind="hot" title="Browser · token here">Receives the access token and calls APIs with it.</Box>
<Arrow sym="↔">sends its cookie,<br />gets a token back</Arrow>
<Box title="Backend">Does the OAuth exchange, hands the token over.</Box>
</Flow>

<Flow>
<Box kind="hot" title="Browser · token here">Token in memory.</Box>
<Arrow>Bearer token<br />direct</Arrow>
<Box title="Resource server">Your API</Box>
</Flow>

<FlowCaption>The refresh token stays server-side, which is the improvement over pattern 3. The access token does not, which is the gap against pattern 1.</FlowCaption>

#### 3 — Browser-based OAuth client · not recommended for sensitive apps

<Flow>
<Box kind="hot" title="Browser · token here">Public client. Runs the whole flow, holds every token.</Box>
<Arrow sym="↔">Authorization Code<br />+ PKCE</Arrow>
<Box title="Authorisation server">Issues tokens straight to the browser</Box>
<Arrow>Bearer token</Arrow>
<Box title="Resource server">Your API</Box>
</Flow>

<FlowCaption>Every credential lives inside the XSS blast radius. In a micro-frontend that radius contains every other team's code and every dependency any of them added.</FlowCaption>

### The cookie checklist

§6.1.3.2 is unusually prescriptive for an RFC. Treat it as a literal checklist:

- <q>The BFF **MUST** enable the `Secure` flag for its cookies.</q>
- <q>The BFF **MUST** enable the `HttpOnly` flag for its cookies.</q>
- <q>The BFF **SHOULD** enable the `SameSite=Strict` flag for its cookies.</q>
- <q>The BFF **SHOULD** set its cookie path to `/`.</q>
- <q>The BFF **SHOULD NOT** set the `Domain` attribute for cookies.</q>
- <q>The BFF SHOULD start the name of its cookie with a prefix indicating the cookie was set via HTTP, for example, by using the `__Host-Http-` prefix.</q>

<Moved title="The Domain rule">
The common advice for micro-frontends is “set a cookie on the shared parent domain so every sub-app can use it.” The RFC says not to, and it is right.

A cookie without `Domain` is [host-only](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie): <q>If omitted, the cookie is returned only to the host that sent it.</q> With `Domain=example.com` it is readable by *every* subdomain, so one compromised subdomain compromises the session everywhere. `__Host-` prefixed cookies structurally cannot carry `Domain` at all.

**The reconciliation:** the BFF design makes the parent-domain cookie *unnecessary* rather than merely forbidden. If all API traffic is proxied through the BFF's own origin, a host-only cookie already reaches everything. Needing a `Domain` cookie is a signal that you have sub-apps calling different backends directly — that is the smell, not the cookie.
</Moved>

<Trap title={<><code>SameSite=Strict</code> and inbound links</>}>
A `Strict` cookie is not sent on cross-site navigation. A user following a link from email or a partner site arrives *logged out* until a same-site request fires. The RFC still says `Strict` — so handle it with a silent re-authentication bounce, not by quietly downgrading to `Lax`.
</Trap>

### CSRF — the bill that comes with cookie sessions

This guide has recommended cookie-based sessions throughout, and until now said nothing about the class of attack that recommendation reopens. A cookie is attached by the browser *automatically*, on requests your application did not initiate. That is the entire point of a cookie and the entire mechanism of CSRF.

Bearer tokens in JavaScript were immune to this, because an attacker's page cannot read your memory to construct the header. Moving to cookies trades an XSS exposure for a CSRF exposure. You have to close the second one deliberately.

<Trap title={<><code>SameSite=Strict</code> is not a CSRF defence on its own</>}>
The most common mistake after adopting a BFF: assuming the cookie flags from the checklist above finished the job. [OWASP is direct about this](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html):

<Quote>`SameSite` is useful as a defense-in-depth control but it does not replace a proper CSRF defense in most deployments.</Quote>

The gap that matters most for micro-frontends is the second one they list: <q>**`SameSite` is scoped to the registrable domain, not the origin.** A cookie set on `app.example.com` with any `SameSite` value is still considered “same-site” when the request originates from `anything.example.com`.</q>

If your teams deploy to sibling subdomains — which is exactly what a micro-frontend estate looks like — every sibling is inside your same-site boundary. OWASP names the amplified version: an attacker who claims a dangling subdomain <q>can issue requests that your `SameSite`-protected cookies will accompany.</q>
</Trap>

Their other documented gaps, each worth checking against your own estate:

- **`Lax` only blocks unsafe methods.** <q>If any state-changing operation in the application is reachable via a `GET` request, `SameSite=Lax` will not stop it. This is the single most common way `SameSite`-based defenses fail in practice.</q>
- **Top-level navigation tricks.** `window.open`, a crafted link or a prerender hint can produce a request the browser treats as same-site.
- **Coverage is not universal.** Older and embedded browsers may behave as if no `SameSite` value were set.
- **Client-side CSRF is untouched.** `SameSite` reasons about cross-site requests; it does nothing about your own same-origin JavaScript being manipulated into a state-changing call.

#### What to actually implement

OWASP's summary recommendation, in order:

1. **Use your framework's built-in CSRF protection** if it has one. If not, <q>add CSRF tokens to all state-changing requests... and validate them on the backend.</q>
2. **Stateful backend → synchronizer token.** Generated server-side, per session or per request. Per-request is stronger, at some usability cost.
3. **Stateless backend → signed double-submit cookie**, and specifically the signed variant: <q>Simply signing tokens without session binding provides minimal protection and remains vulnerable to cookie injection attacks. Always bind the CSRF token explicitly to session-specific data.</q> The naive double-submit pattern is documented by OWASP as **discouraged** for new code.
4. **Send the token in a custom request header, not a form field.** <q>Since requests with custom headers are automatically subject to the same-origin policy, it is more secure to insert the CSRF token in a custom HTTP request header via JavaScript.</q> For an API-shaped BFF this is the natural fit, and a custom header alone is a legitimate defence for AJAX endpoints.
5. **Verify `Origin`, falling back to `Referer`,** on every state-changing endpoint. These are [forbidden headers](https://developer.mozilla.org/en-US/docs/Glossary/Forbidden_header_name) that only the browser can set. OWASP recommends **blocking** when neither is present.

<Insight title="Where this lives in a micro-frontend">
The BFF already owns the session, so it must also own CSRF. One token, minted by the BFF, exposed to micro-frontends through the shell's `getCsrfToken()` — the same tiny shell-owned contract from <Mod to="sharing" />, extended by one method.

Per-micro-frontend CSRF tokens are the failure mode here. They multiply the surface, they break the moment one team's token is rotated by another team's request, and they tempt somebody into widening the cookie's `Domain` to share them — which reintroduces the exact subdomain weakness above.
</Insight>

### Sessions, not just tokens

The chapter so far has been about OAuth architecture. The session itself has its own lifecycle, and [OWASP's session management guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) covers the parts that are easy to skip.

#### Rotate the session ID on privilege change

A new session identifier must be issued at login, and again at any privilege elevation — step-up MFA, entering an admin context, impersonation. This is the defence against [session fixation](https://www.acrossecurity.com/papers/session_fixation.pdf), where an attacker plants a known session ID before the victim authenticates and inherits the authenticated session afterwards. Reusing the pre-login identifier is the vulnerability.

OWASP also warns against the condition a micro-frontend estate creates by default: <q>it is recommended not to mix web applications of different security levels on the same domain. Vulnerabilities in one of the web applications would allow an attacker to set the session ID for a different web application on the same domain by using a permissive `Domain` attribute.</q> A third argument against the `Domain` cookie, from a different direction.

#### Two timeouts, not one

| Timeout | Measured from | What it limits | OWASP's ranges |
| --- | --- | --- | --- |
| **Idle** | Last request | The window for using a stolen ID on an abandoned session. Does *not* constrain an active attacker, who can keep it alive with traffic. | <q>2-5 minutes for high-value applications and 15-30 minutes for low risk applications</q> |
| **Absolute** | Session creation | Total lifetime regardless of activity. This is the one that eventually evicts a hijacked session. | <q>between 4 and 8 hours</q> for a full working day |

You need both, for the reason in the table: idle timeout alone never expires an attacker who is actively using the session.

#### Logout has to invalidate the server side

<Source>
<Quote>When a session expires, the web application must take active actions to invalidate the session on both sides, client and server. **The latter is the most relevant and mandatory from a security perspective.**</Quote>

<Cite>— [OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)</Cite>
</Source>

Clearing the cookie is the cosmetic half. A logout that only deletes the client cookie leaves a session that still validates if the value was captured. In a BFF, one logout must clear the cookie, destroy the server-side session record, **and** revoke the refresh token at the authorisation server — otherwise the BFF can mint a new access token for a user who believes they have left.

#### And logout has to propagate

Two propagation problems that only appear once the frontend is split:

- **Across micro-frontends in one tab.** The shell logs out; every mounted micro-frontend still holds rendered user data and possibly an open socket. The shell needs to broadcast a `session:ended` event and each micro-frontend must clear and unmount on it — the same event contract from <Mod to="sharing" />, and the one case where ignoring the event is a security bug rather than a staleness bug.
- **Across tabs.** Other tabs keep rendering a logged-in UI against a dead session until their next request fails. `BroadcastChannel` or the `storage` event closes it. This is also the mechanism for the reverse case: a login in one tab should refresh the others rather than leaving them in a stale anonymous state.

### Where authorization lives

Everything above is authentication. Authorization is a separate decision that micro-frontend teams routinely leave implicit, and there are only three places to put it.

| Placement | Good for | Cost |
| --- | --- | --- |
| **Resource server**<Sub>the only one that is load-bearing</Sub> | Every actual enforcement decision. Non-negotiable: this is the only layer an attacker cannot skip. | None. It is required. |
| **BFF** | Coarse route gating, so an unauthorised user does not reach a shell they cannot use. | Duplicates policy in two places; they drift. |
| **Browser** | Hiding controls the user cannot use. **Presentation only.** | Tempting to treat as enforcement. It is not — every check is editable by the person it applies to. |

The practical question is what claims the shell publishes. Shipping a full permission set to the browser makes every micro-frontend's UI easy and leaks your authorization model to anyone who opens devtools. Shipping nothing means each micro-frontend fetches its own permissions and you get the `/me` fan-out described under *Supporting specs* below. The usable middle: the shell exposes a small, coarse set of *capability flags* — `canManageBilling`, not the role graph — purely to decide what to render, with the resource server enforcing the real thing on every call.

### Auth during server rendering

Expanding the one-line rule from earlier, because this is where composed pages leak.

- **Propagate, do not re-authenticate.** The inbound request's identity travels to every internal call and every fragment render — Podium's context headers (<Mod to="streaming" />) exist for exactly this.
- **Never cache user data at module scope.** In a long-lived Node process, a module-level variable is shared across every concurrent request. This is the highest-severity bug in this entire guide: it serves one user's data to another, it passes every test that runs one request at a time, and it appears under load.
- **An authenticated render is not CDN-cacheable**, which is the cacheability floor from <Mod to="micro-frontends" /> arriving as a security constraint rather than a performance one. Keep the personalised part behind its own boundary and stream it.
- **Decide what a mid-stream auth failure renders.** Once the shell has flushed, you cannot send a redirect — the status line is long gone. The fragment must degrade to a signed-out state inside its own boundary, and the shell must be designed to survive that.

### Token storage — the RFC is blunt

<Source>
On `localStorage`: <q>localStorage does not protect against unauthorized access from malicious JavaScript, as the attacker would be running code within the same origin, and as such, would be able to read the contents of the localStorage.</q>

On JavaScript-readable cookies: <q>this practice is NOT RECOMMENDED.</q>

And the honest general conclusion: <q>none of these options can fully mitigate token exfiltration when the attacker can execute malicious code in the application's execution environment.</q>

Also non-negotiable: <q>Browser-based clients MUST use the Authorization Code grant type and MUST NOT use the Implicit grant type to obtain access tokens.</q>

<Cite>— [RFC 10017 §8](https://www.rfc-editor.org/info/rfc10017/)</Cite>
</Source>

<Insight title="Why this compounds in micro-frontends">
N teams' code, **one origin, one JavaScript heap.** Every micro-frontend sits inside every other one's XSS blast radius. A third-party dependency added by any team can read what any other team put in memory.

The strongest argument for keeping tokens out of the browser entirely — stronger here than in a monolith.
</Insight>

### Supporting specs and the practical rules

- [RFC 9700](https://www.rfc-editor.org/info/rfc9700) (BCP **240**, not 212): <q>Refresh tokens for public clients MUST be sender-constrained or use refresh token rotation.</q> Also <q>The resource owner password credentials grant \[RFC6749\] MUST NOT be used.</q>
- Foundations: [RFC 6749](https://www.rfc-editor.org/info/rfc6749) (framework), [RFC 6750](https://www.rfc-editor.org/info/rfc6750) (bearer tokens), [RFC 7636](https://www.rfc-editor.org/info/rfc7636) (PKCE).
- **The shell owns token refresh.** Never let each micro-frontend run its own refresh loop — you get a thundering herd on expiry and a race on rotation that logs users out at random. Common, and very hard to diagnose.
- **Proxy API calls through one origin** rather than configuring CORS with credentials across N origins. Note [a wildcard origin is rejected when credentials are used](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS/Errors/CORSNotSupportingCredentials) — the server must echo the specific origin.
- **Deduplicate the fan-out.** Five micro-frontends each calling `/me` on load is the signature performance bug of this architecture.
- **On the server side:** SSR calls go over the internal network, propagate the inbound auth context and a trace ID, and never cache user data at module scope — in a long-lived Node process that is a cross-user data leak.

### Third-party cookies: the ground moved twice

<Moved>
If your micro-frontends live on different origins or in iframes, this matters directly. Chrome **reversed** the third-party cookie deprecation, and in an [October 2025 Privacy Sandbox post](https://privacysandbox.google.com/blog/update-on-plans-for-privacy-sandbox-technologies) announced it is retiring most of the replacement APIs — including Topics, Protected Audience, Attribution Reporting, Related Website Sets and Shared Storage.

What survives: <q>CHIPS and FedCM… We'll continue to support those APIs. We'll also maintain Private State Tokens.</q> So [CHIPS / partitioned cookies](https://developer.mozilla.org/en-US/docs/Web/Privacy/Guides/Third-party_cookies/Partitioned_cookies) is the durable mechanism for cross-origin embedded micro-frontends.
</Moved>

<Recap>
- RFC 10017 (Aug 2026) strongly recommends the BFF for anything sensitive, and does not recommend a pure browser OAuth client for it.
- Cookies: `Secure` + `HttpOnly` MUST; `SameSite=Strict`, path `/`, `__Host-Http-` prefix and *no* `Domain` SHOULD.
- **Cookies reopen CSRF.** `SameSite` is defence in depth, not a defence — it is scoped to the registrable domain, so every sibling subdomain is inside your boundary. Add a signed double-submit or synchronizer token, in a custom header, plus `Origin` verification.
- Rotate the session ID at login and at every privilege change. Run **both** an idle and an absolute timeout — idle alone never expires an active attacker.
- Logout must destroy the server-side session and revoke the refresh token, then propagate across micro-frontends and across tabs. Clearing the cookie is the cosmetic half.
- Authorization is enforced at the resource server. The browser gets coarse capability flags for rendering, never the role graph, and never enforcement.
- During SSR: propagate identity, never cache user data at module scope, and decide in advance what a mid-stream auth failure renders.
- No token storage in the browser is safe against XSS — and micro-frontends enlarge the blast radius.
- The shell owns refresh. One origin for API traffic. Deduplicate `/me`.
- Third-party cookies survive in Chrome; CHIPS and FedCM are the surviving Privacy Sandbox pieces.
</Recap>
