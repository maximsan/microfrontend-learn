### First: not all of these decisions cost the same to undo

The guide has so far treated every choice as equally weighty. They are not, and the difference should govern how much analysis each one gets. Spend your thinking where the door only opens one way.

| Decision | Cost to reverse | Why |
| --- | --- | --- |
| **Micro-frontends, yes or no** | <Rev kind="oneway" /> | Reversing means re-merging independently deployed codebases and dissolving the team boundaries that justified them. Spotify needed a full rewrite (Module 06). |
| **Auth architecture** | <Rev kind="oneway" /> | Moving tokens out of the browser touches every API call, every client, and invalidates every live session. Retrofitting a BFF onto a token-holding SPA is a migration, not a refactor. |
| **Local-first / sync engine** | <Rev kind="oneway" /> | Conflict resolution and offline semantics leak into the data model and into the product's behaviour. Users notice when you remove it. |
| **SPA vs server-rendered** | <Rev kind="costly" /> | Reversible, and Netflix and Contexte both did it — but it is a rewrite of the view layer, not a config change. |
| **Composition point** | <Rev kind="costly" /> | Zones → fragments → federation each imply different deploy topology and ops. Changing it is a quarter, not a sprint. |
| **Public API shape** | <Rev kind="costly" /> | Versioning buys you an exit, but you carry both shapes until every client migrates. |
| **Monorepo vs polyrepo** | <Rev kind="cheap" /> | History rewriting is annoying and well-trodden. Deployment independence is unaffected either way (Module 11). |
| **Bundler** | <Rev kind="cheap" /> | Config and CI. webpack → Rspack is close to a drop-in. Teams agonise over this one and should not. |
| **Router library** | <Rev kind="cheap" /> | Contained to the view layer, mechanical to swap. |
| **Realtime transport** | <Rev kind="cheap" /> | SSE ↔ WebSocket is an adapter, provided you kept it behind one. |

Read the sequence below in that light: **steps 2 and 4 are one-way doors and step 5 is not.** The common failure is inverting this — a long bundler debate, and auth decided in an afternoon because it felt like plumbing.

### The decision sequence

1. **Measure session length and interaction density.** This settles the SPA question more often than any architectural debate will.
2. **Ask whether independent deployment is a hard requirement.** If teams can ship together, do not build micro-frontends. You want faster builds, and runtime composition is the wrong tool for that.
3. **If it is a hard requirement, choose your composition point** before choosing any tool.
4. **Design auth before anything else.** It is the hardest thing to retrofit and the most damaging to get wrong. [RFC 10017](https://www.rfc-editor.org/info/rfc10017/) gives you a checklist — §6 for the architecture, §6.1.3.2 for the cookie flags.
5. **Pick tooling last.** By this point the constraints have narrowed the options to one or two.

**Streaming is orthogonal to the rest of the tree.** It is not a competing mode — it is a modifier you layer onto any request-time rendering when a data source is slow. And if several teams compose this route, check the cacheability floor in Module 06 before committing to a leaf: one team's per-user fragment can invalidate the caching the other leaves depend on.

#### Fixed regardless of which leaf you reached

- **Auth** — BFF, host-only `__Host-` cookies, no tokens in the browser ([RFC 10017](https://www.rfc-editor.org/info/rfc10017/)).
- **Realtime** — one shell-owned connection, fanned out. Never one per micro-frontend.
- **History** — exactly one owner, built on the Navigation API.
- **Repository** — a monorepo does not couple deployments, and it kills dependency drift.

### A defensible 2026 default

| Layer | Choice | Why |
| --- | --- | --- |
| **Composition** | Routing-level zones behind a proxy | Independent failure domains, no shared bundler config, boring failure modes |
| **Escalation** | Podium fragment streaming | Only when several teams must appear on one screen *and* SEO matters |
| **Repository** | Monorepo, pnpm workspaces, Turborepo or Nx | Kills dependency drift; per-app affected deploys keep releases independent |
| **Bundler** | Rspack or Vite | Not Next.js (federation deprecated), not Parcel (no MF), not Turbopack (no webpack plugins) |
| **Routing** | Shell owns history, built on the Navigation API | Baseline since Jan 2026 — no monkey-patching for new work |
| **Auth** | BFF per RFC 10017 | Host-only `__Host-` cookies, `Secure`, `HttpOnly`, `SameSite=Strict`, no tokens in the browser |
| **API** | BFF per team, or GraphQL federation | Front-end and back-end boundaries align; no shared-API committee bottleneck |
| **Realtime** | One shell-owned SSE or WebSocket | The six-connection cap is per browser, per domain, across all tabs |

### Four questions that should stop you

1. **Can our teams deploy together today?** If yes, you do not need micro-frontends, and Nx's documentation will tell you so in writing.
2. **Do two of our proposed micro-frontends need to share mutable state?** If yes, the boundary is drawn wrong. Redraw it before writing integration code.
3. **Are we planning to put tokens in the browser?** If yes, read RFC 10017 §6 and §8 and make the decision explicitly, with the risk written down.
4. **Is our chosen tool still maintained?** In this specific area the answer is “no” far more often than experience suggests. Check the repository, not the blog post.

<Insight title="The one question">
Every architecture in this guide answers the same thing: *where does the long-lived state live, and who is allowed to touch it?*

Rendering, routing, transports, auth and delivery are all downstream of that. Decide it; do not inherit it from a starter template.
