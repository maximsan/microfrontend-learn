With the dividing line established, the landscape orders itself. The axis runs from <ServerSide>server owns everything</ServerSide> to <ClientSide>client owns everything</ClientSide>, and the useful question for any architecture is: at what point does the HTML come into existence, and who holds the truth afterwards?

### The variants in full

| Variant | Who builds the HTML | Reach for it when | Avoid when |
| --- | --- | --- | --- |
| **Static documents** | Nobody — files on a CDN | Content that changes on a deploy cadence | Anything per-user |
| **Classic MPA** | Server, per request | Forms and CRUD, SEO matters, one team, one language | Sub-100 ms interaction is required |
| **MPA + AJAX** | Server, plus JS-fetched fragments | Mostly content with a few hot spots | The hot spots become the whole page |
| **Hypermedia** | Server, fragments swapped in place | SPA feel, server-side team, server-owned state | Canvas, drag-and-drop, offline, real-time collaboration |
| **LiveView / Blazor Server** | Server, diffs over a socket | Low-latency networks, rich server-driven UI | High RTT, or server RAM per user is a concern |
| **SPA (CSR)** | Client | Long sessions, dense interaction, offline, you already need an API | Public content, read-and-leave, low-end devices |
| **SSR + hydration** | Server first paint, client after | SPA interactivity *and* SEO / fast first paint | The interactive surface is 5% of the page |
| **Static generation** | Build time, then client | Content sites with app-like pockets | Per-request or per-user content |
| **Islands** | Server; JS only for interactive regions | Content-dominant page, strict JS budget | Genuinely app-like UI where everything is interactive |
| **Server Components** | Split per component | Data-heavy UI, server data access without an API layer | Small team with low tolerance for framework churn |
| **Local-first** | Client, from a local database | Offline is a requirement, or real-time collaboration | Strong consistency or auditability requirements |

Two of these are worth more than the rest. **Contexte** and **Netflix** are the only entries where a team moved *backwards* along the axis and published the numbers — which makes them the closest thing in this guide to evidence rather than reasoning.

### Two things that are not on this axis

**Progressive Web Apps** are orthogonal. A service worker, a manifest, offline capability and installability can be bolted onto an MPA as easily as onto a SPA. PWA describes distribution and offline behaviour, not rendering.

**Micro-frontends** are also orthogonal, and more consequentially so. They are an organisational and deployment concern. You can build an MPA composed of independently-deployed SPAs — <Mod to="micro-frontends" /> argues that is usually the right shape. Confusing “we need micro-frontends” with “we need a SPA” produces some of the worst architectures in the field.

<Insight title="The one discriminator">
**How long is a session, and how dense are the interactions inside it?**

Read-and-leave, low density → server-rendered HTML. Live-in-it-all-day, high density → SPA. Everything else is secondary, and both numbers are already in your analytics.
</Insight>

<Recap>
- One axis: where the HTML is built and who holds the truth afterwards. Eleven recognisable positions on it.
- PWA is orthogonal — it describes offline and installation, not rendering.
- Micro-frontends are orthogonal and organisational. An MPA of independently-deployed SPAs is coherent and often correct.
- Session length × interaction density settles most cases.
</Recap>

2. Why are Contexte and Netflix worth more than the other rows in *In the wild*?
3. An internal admin tool is open all day and every screen is filters, inline edits and drag-and-drop. Where does it sit on the axis, and which two numbers justify that?

<Answers>
1. **It conflates two orthogonal axes.** Micro-frontends are an organisational and deployment decision; SPA is a rendering decision. An MPA made of independently deployed SPAs — routing-level zones — is coherent and often the right shape (<Mod to="micro-frontends" />). Treating one as implying the other produces some of the worst architectures in the field.
2. **They moved backwards along the axis and published numbers.** Contexte cut its code base by 67% moving from React to Django + htmx; Netflix made a landing page 50% faster by removing client-side React. Every other row shows *what* someone runs; these two show what happened when a team changed position — the closest thing to evidence rather than reasoning.
3. **Toward the client — a SPA, or hypermedia if the team is server-side and state is server-owned.** The justification is the chapter's one discriminator: *session length* and *interaction density*. Both are high, so the bundle cost amortises and per-interaction round trips would dominate the experience.
